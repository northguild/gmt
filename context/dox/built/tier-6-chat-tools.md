# Tier 6: Dox, chat widget tools

Part of [built/index.md](index.md). The chat surface, request pipeline and client: [tier-6-chat.md](tier-6-chat.md).

- Schemas are shared by client and Worker in `src/lib/dox-tools.ts`; read the arguments there. Rules that every tool schema follows: pass what the reader gave, exactly as typed (never trimmed or corrected); pass a zone only when the reader named it, never chosen from a port, place, facility, partner, code or abbreviation; a required window, basis or direction the library requires stays required and a blank stays blank; a zoneless wall time is read in the named zone with `disambiguation: "reject"`; a code check validates shape only (`ediCodeSchema`) so a code the library refuses is the widget's sentinel, not a failed call; never supply a place's holidays, policy or calendar from memory.
- A Worker tool's `execute` is `accept("<name>")` (the Canada and Morocco tools refuse any id outside `canada-zones.json` or `morocco-region-zones.json`; the registry's `validate` checks the same lists, and Sunshine Protection Act checks `us-region-zones.json` and `STATE_CODES`).
- Counts: `ENABLED_TOOL_NAMES` and `CHAT_STARTERS` hold the numbers, one starter card per tool. Never write a literal count in a test or a page. Parity: `ENABLED_TOOL_NAMES` equals the registry keys (`widget-registry.test.ts`) and every enabled tool has a `CHAT_STARTERS` card (`chat-starters.test.ts`).
- Every new Dox tool ships with its `CHAT_STARTERS` card and chat widget registration.
- Tools are offered per question (`worker/select-tools.ts`), at most eight: the first five `CHAT_STARTERS` widgets (`CORE_TOOL_COUNT`, so the order of the first five starters decides the core tools), the best three matches from a MiniSearch index over name, purpose and `Call when` (plus a bonus for a tool naming a function retrieval ranked high), and every tool the conversation already called (a provider can reject a history that calls an undeclared function). `select-tools.test.ts` checks each starter's widget is offered for its question; a starter that misses needs better `Call when` wording, not a larger set. The full-text score is divided by the best match's, so the retrieval bonus (`RETRIEVAL_WEIGHT`) weighs the same against a long question as a short one; terms stem `-er` and match by prefix from four letters, and `args` is indexed at a low weight.
- Tool prompt wording: "When the question matches a `Call when` line, call that tool" works. Prose first, at most one tool, no default widget, never invent a zone.
- Example cards (`ExamplesPanel.tsx`) live in the widget rail, grouped by `EXAMPLE_AREAS` (industries, with each industry's icon; a card's `area` is its tool page's tag; no area for an industry with no tool). A card is a native `<button>`; activating it sends the question and, only if the send went, calls the rail with `starterWidgetCall(starter)`. The model's own call replaces it unless `isSameWidget` says tool and arguments match. `chat-starters.test.ts` runs every seed through its schema and `validate`.
- Rail: `aria-label="Examples"` with the list, `Widget panel` with a widget. Below 60rem it is the bottom sheet (`data-empty` on `.gmt-hive-body`; `ExamplesBar.tsx` toggles it). Activating a card moves focus to the widget title; a widget the model opens never takes focus; closing returns focus to that tool's card, else the bar. Read `matchMedia` in handlers and effects only, never during render (#418). `DoxPage` owns `conversationStarted`, `examplesOpen`, the rail widget and focus requests; `DoxChat` stays host-agnostic (`rail-keyboard.test.tsx`).
- Worker tools carry a trivial `execute` (`worker/tools.ts`); without one a replayed turn has a tool call with no result and the provider rejects the next question (`tools.test.ts`). `convertToModelMessages` runs with `ignoreIncompleteToolCalls: true`.
- One step, unless the widget came alone (`WIDGET_THEN_PROSE`, `worker/brains.ts`): a step 1 that called a tool and wrote nothing gets one more step with every tool off (`prepareStep` with `activeTools: []`). Step 2 runs after the stream opens, so it cannot fail over; if it fails the reader keeps the widget and sees the error after it.
- `toolCallMarkupMiddleware` (`worker/tool-call-markup.ts`) handles a tool call a model wrote as text, in two forms: GLM's `<tool_call>name<arg_key>k</arg_key><arg_value>v</arg_value></tool_call>` and Gemma's `<|tool_call>call:name{k:<|"|>v<|"|>}<tool_call|>`. The text never reaches the reader: a tag split across deltas is held back until it is known to be a tag, an unclosed call is dropped, and a block that held only markup is dropped whole. If the step made no real call, each complete written call to a tool on offer becomes a real `tool-call`; if it made one, the written ones are only dropped, so a widget never opens twice. An unreadable call, or one naming a tool not on offer, is only dropped. Gemma values are typed against the tool's schema. The live eval's `markup` check fails an answer that still carries either form ([tier-6-evals.md](tier-6-evals.md#graders)).
- A tool call whose input fails its schema goes through `repairToolCall` (`worker/repair-tool-call.ts`, `tool-input-coercion.ts`) before the reader sees an error. It runs only for an invalid input, makes no model call and changes only the type of a value the model already gave (a number for a string, a string for a number); it never adds, removes or guesses a value, and the SDK validates the result again. A call still invalid after that shows "The assistant could not open that tool this time. Ask again, or open the tool from its page." (retryable, `worker/error-mapping.ts`).
- The client never trusts tool input: `widget-registry.ts` re-validates at mount and checks zones with `isValidTimeZone`. The registry is fixed and typed with a literal `import()` per mount; no `eval`. `showPlayground` was cut to keep that true. An entry's `load()` returns `{ renderTemplate, mount }`; the registry imports only types from mount modules. `widget-graph.test.ts` fails if the island's static value imports reach a mount, `gmt-modules.ts`, a widget's logic, a direct polyfill import or gmt's root barrel. Chat code imports gmt by module path because the root barrel re-exports the polyfill.
- `MountedWidget.tsx` renders an empty host (`aria-busy` until wired); the DOM lives outside React and an `AbortSignal` handles StrictMode's double effect. A `WidgetLoadError` or failed `import()` shows an error with Try again; a bad argument gets no retry.

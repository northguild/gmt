# AV-28 — Aviation: Aeronautical timestamps, schedules, curfews and slots

**Scope:** NOTAM validity and schedules, METAR and TAF report and forecast times, airport curfews, and ATFM slot windows.

## Gap

Aeronautical messages carry timestamps in formats no general date library parses, and several of them are ambiguous without external context.

- **NOTAM** items B) and C) use a ten-digit `YYMMDDHHMM` group, plus the non-numeric values `EST` (estimated end) and `PERM` (permanent, no expiry). Item **D)** is a *schedule* inside that validity: "A NOTAM is active between the dates and times stated in Items B) and C) subject to the time schedule in Item D)". The OPADD rules are exact — "Item D) shall contain either days of the week (MON, TUE,...) or dates (01 02 03...)", never both; "The start of the first activity in Item D) shall always correspond to the Item B) date and time" and the last to C); gaps between activities "shall not exceed 7 days"; the item "shall not exceed 200 characters"; the tokens are day names, dates, `HHMM` times, `DAILY`, `EVERY`, `H24` (never as a single entry), `EXC` for excluded days, `SR`/`SS` with `SR MINUS**mm` / `SS PLUS**mm` (a space after `SR`, up to 99 minutes), a hyphen for FROM-TO, and no oblique. A parser returning only a timestamp cannot represent any of it.
- **METAR and TAF** report times are `DDHHMMZ` — day of month, hour, minute, **no month and no year**. Parsing one *requires* a reference instant, and near a month boundary the nearest candidate is in the previous or next month. TAF forecasts add a validity period `Y1Y1G1G1/Y2Y2G2G2` (`DDHH/DDHH`, where a period ending at midnight is written with hour `24`) and change groups — `FMYYGGgg`, which supersedes everything before it; `BECMG YYGG/YeYeGeGe`, whose window "shall normally not exceed two hours and in any case shall not exceed four hours"; `TEMPO YYGG/YeYeGeGe`, for conditions lasting "less than one hour in each instance" and "less than half of the period"; and `PROB30`/`PROB40`, the only permitted probabilities, never combined with `BECMG` or `FM` — every one of which needs the same month resolution.

([EUROCONTROL OPADD Edition 4.1, §2.3.18–2.3.21 Item D), ICAO APAC-hosted copy](https://www.icao.int/sites/default/files/sp-files/APAC/Documents/EUROCONTROL%20Operating%20Procedures%20for%20AIS%20Dynamic%20Data%20(OPADD)%20Edition%204.1.pdf), [FAA NOTAM primer](https://www.faa.gov/sites/faa.gov/files/about/initiatives/notam/what_is_a_notam/Pilots_NOTAM_primer_for_2021.pdf), [WMO-No. 306 Vol. I.1 Part A, FM 51 TAF, regulations 51.1.4, 51.8.1–51.8.4, 51.9.1–51.9.3](https://www.eoas.ubc.ca/courses/atsc303/Instruments/wmo_guides/wmo_306-vI1_en-2013.pdf), [IVAO CTOT](https://wiki.ivao.aero/en/home/training/documentation/Calculated_take-off_time), [EUROCONTROL slot adherence](https://www.eurocontrol.int/prudata/dashboard/metadata/atfm-slot-adherence/))

## Scope

- `packages/gmt/src/aviation/parse/notamValidity.ts`:
  - `parseNotamValidity(value: string): { at: string, estimated: boolean } | { permanent: true } | null` — Parses a B) or C) field. `'PERM'` yields the permanent form; a trailing `EST` sets `estimated`.
  - `formatNotamValidity(isoString: string, options?: { estimated?: boolean }): string`
- `packages/gmt/src/aviation/parse/notamSchedule.ts`:
  - `parseNotamSchedule(value: string): NotamSchedule | null` — Item D) into a structured schedule: `{ entries: ({ days: 'daily' | number[] } | { dates: { month?: number, day: number }[] }) & { windows: ({ from: string, to: string } | { from: SolarRef, to: SolarRef } | 'H24')[] })[], excluded: { month?: number, day: number }[] }`, where `SolarRef` is `{ event: 'SR' | 'SS', offsetMinutes: number }`. Mixed days and dates, an oblique, `H24` as the only entry, or more than 200 characters return the sentinel, per OPADD.
  - `notamActiveIntervals(schedule: NotamSchedule, validity: Interval, options?: { solar?: (date: string) => { sunrise: string, sunset: string } }): Interval[] | null` — The concrete UTC intervals the NOTAM is active, clipped to B)–C), with `EXC` days removed; the sentinel when the first activity does not start at B) or the last does not end at C), or when consecutive activities are more than 7 days apart. Solar references need the caller's `solar` provider (SPA-75 supplies one); without it a schedule with SR/SS returns the sentinel rather than a guess.
- `packages/gmt/src/aviation/parse/metarTime.ts`:
  - `parseMetarTime(value: string, referenceInstant: string): string | null` — `'251200Z'` resolved against a reference instant, choosing the nearest candidate month.
  - `parseTafPeriod(value: string, referenceInstant: string): Interval | null` — `'1512/1618'` resolved the same way; a `GeGe` of `24` is the end of that day (WMO 306 Note to 51.8.1).
  - `parseTafChangeGroup(value: string, referenceInstant: string): { kind: 'FM' | 'BECMG' | 'TEMPO' | 'PROB30' | 'PROB40' | 'PROB30 TEMPO' | 'PROB40 TEMPO', interval: Interval, windowTooLong?: boolean } | null` — `FM151800` becomes a half-open interval from that instant to the end of the validity or the next `FM`; `BECMG` sets `windowTooLong` when its window exceeds four hours; `PROB` with `BECMG` or `FM`, or a probability other than 30 or 40, returns the sentinel (51.9.1, 51.9.3).
- `packages/gmt/src/aviation/calculate/airportCurfew.ts`:
  - `airportCurfew(isoString: string, curfew: { start: string, end: string, timeZone: string }): { inCurfew: boolean, curfewStart: string, curfewEnd: string } | null` — Curfew is caller-supplied.
- `packages/gmt/src/aviation/calculate/slotWindow.ts`:
  - `slotWindow(ctot: string, options?: { before?: string, after?: string }): Interval` — The slot tolerance window around a Calculated Take-Off Time. Defaults to −5/+10 minutes.
  - `isWithinSlot(actualTakeoff: string, ctot: string, options?): boolean`

## Formats and constants

| Item | Format | Notes |
| --- | --- | --- |
| NOTAM B) / C) | `YYMMDDHHMM` | Ten digits, UTC. C) may be `PERM`, or a DTG followed by `EST` |
| NOTAM D) | `DAILY`, `EVERY`, `MON-FRI`, `MON WED FRI`, dates `01 02 …`, `HHMM-HHMM`, `H24`, `SR`, `SS`, `SR MINUS30`, `SS PLUS30`, `EXC` | Days **or** dates, never both; first activity = B), last = C); gaps ≤ 7 days; ≤ 200 characters; no oblique; no year (OPADD 2.3.18–2.3.20) |
| METAR / TAF | `DDHHMMZ` | Day, hour, minute — **no month or year** |
| TAF validity | `DDHH/DDHH` | Second group may be `DD24` for midnight (WMO 306, Note to 51.8.1) |
| TAF change groups | `FMDDHHMM`, `BECMG DDHH/DDHH` (≤ 2 h normally, ≤ 4 h always), `TEMPO DDHH/DDHH`, `PROB30`/`PROB40 [TEMPO] DDHH/DDHH` | Same month-resolution problem as the report time; PROB never with BECMG or FM |
| ATFM slot | CTOT −5 / +10 min | A CTOT of 10:15 permits take-off from 10:10 to 10:25 |

## Design notes

- **`PERM` is not a date, and `EST` is not a certainty.** Both must survive parsing as distinct states. Coercing `PERM` to a far-future timestamp is the standard wrong answer, and it makes every "is this NOTAM active" query silently correct-looking and wrong at the boundary.
- **Item D) is a recurring window inside a validity, which is CORE-55's model.** `notamActiveIntervals` is `recurringWindows` clipped to B)–C); the parsing is aviation-specific, the expansion is not.
- **Sunrise and sunset are not GMT's to guess.** ICAO's own rule is that the actual sunrise on the first day and the actual sunset on the last day are used, which needs the aerodrome's coordinates and a solar model. The `solar` provider parameter keeps this story free of astronomy while letting SPA-75 plug in; a schedule that needs it and lacks it returns the sentinel.
- **METAR and TAF resolution needs a reference and can still be wrong**, which is why the reference is required rather than defaulting to "now". A report received at 00:05 on the 1st carrying `312350Z` belongs to the previous month. TAF periods and change groups reuse the identical rule so the forecast cannot straddle two resolutions.
- **Curfews are caller-supplied.** The original spec hardcoded a four-airport table (Heathrow, Frankfurt, Sydney, Narita). Curfews change by regulation and by political decision, and four airports is not a useful registry — see [../painpoints.md](../painpoints.md). Convenience data, if any, ships behind the opt-in `@northguild/gmt/aviation/data` subpath.
- Curfew windows cross midnight (23:00–06:00), so the interval logic must handle wrap-around in the airport's local zone, including on DST-transition nights when the window is 23 or 25 hours from the previous one. That wrap is CORE-55's `recurringWindows`, not a local special case.

## Corrections

The original AV-2 described `notamTimestamp` as parsing `DDHHMM` — "`251200` = 25th day, 12:00 UTC". That is the METAR/TAF format, not the NOTAM one; ICAO NOTAM items B) and C) are ten-digit `YYMMDDHHMM`. The spec also had no representation for `EST` or `PERM`, both of which appear routinely in item C), and no notion of item D) at all. The two formats are now parsed by separate functions, because only one of them is ambiguous.

## What gmt provides (do not re-implement)

- `intervalContains` / `intersectIntervals` from CORE-6 — curfew and slot windows
- `resolveLocal` from CORE-4 — local curfew boundaries
- `recurringWindows` from CORE-55 — item D) expansion and midnight-wrapping curfews
- `spanMs` from CORE-2 — nearest-candidate selection for METAR
- `regex/` — existing pattern matchers

## Verification

- `parseNotamValidity('2506151200')` returns the correct instant with `estimated: false`
- `parseNotamValidity('2506151200EST')` returns `estimated: true`
- `parseNotamValidity('PERM')` returns the permanent form, not a timestamp
- `parseNotamSchedule('MON-FRI 0700-1900')` returns weekdays 1–5 and one window; `'MON WED FRI H24, SAT SUN 0600-1700'` (an OPADD example) returns two entries; `'DAILY SR MINUS30-SS PLUS30'` returns solar references with offsets −30 and +30; `'MON-FRI 0600-1700 EXC DEC 05'` returns one excluded date; `'04 1000-06 1200, 08 1200-10 0700'` (the OPADD recommended date syntax) returns two dated windows
- `'MON 0800-1200 05 1400-1600'` (days and dates mixed), `'H24'` alone, and `'MON 0800/1200'` (an oblique) each return the sentinel
- `notamActiveIntervals` over a one-week validity for `MON-FRI 0700-1900` returns five intervals, none outside B)–C); a schedule whose first activity starts after B) returns the sentinel; two activities nine days apart return the sentinel; with an SR/SS schedule and no `solar` provider it returns the sentinel
- `parseMetarTime('312350Z', '2024-07-01T00:05:00Z')` resolves to 31 May, not to the current month — asserted as the previous month's last day
- `parseMetarTime` selects the nearest candidate across a year boundary
- `parseTafPeriod('1512/1618', ref)` returns a 30-hour interval; `'1500/1524'` ends at the start of the 16th
- `parseTafChangeGroup('FM151800', ref)` starts at 18:00 on the 15th; `'TEMPO 1520/1524'` returns a four-hour interval; `'BECMG 1512/1518'` sets `windowTooLong`; `'PROB30 TEMPO 2922/3001'` (the WMO example) parses; `'PROB50 2922/3001'` and `'PROB30 BECMG 2922/3001'` return the sentinel
- A curfew of 23:00–06:00 correctly reports `inCurfew` for 01:00 local
- A curfew evaluated on a DST-transition night returns the correct window bounds
- `isWithinSlot` is `true` at CTOT −5 min and CTOT +10 min, and `false` one second outside either
- Malformed input returns the sentinel
- `pnpm run validate` stays green

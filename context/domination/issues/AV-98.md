# AV-98 — Aviation: METAR report times and NOTAM validity

**Scope:** Resolve a METAR report time, which has no month or year, against a reference instant; read a NOTAM's start and end of validity, including `EST` and `PERM`.

## Gap

Aeronautical messages carry two time forms that look alike and behave differently
([painpoints § Aviation](../painpoints.md#aviation)).

- **A METAR report time has no month and no year.** The group is `YYGGggZ`: "the day of the month
  and the time of observation in hours and minutes UTC followed, without a space, by the letter
  indicator Z". A SPECI carries the same group, and a TAF's issue time uses the same form. Reading
  one needs a reference instant, and near a month boundary the right month is not the reference's:
  a report received at 00:05 on 1 July carrying `302350Z` was made at 23:50 on 30 June. A parser
  that assumes the current month puts it 30 days in the future.
- **NOTAM validity is not that format.** Items B) and C) are ten digits, `YYMMDDHHMM`, in UTC. Item
  C) may instead be `PERM`, or a date-time followed by `EST`. Turning `PERM` into a far-future date
  makes every "is this NOTAM in force" query look right and fail at the boundary, and dropping `EST`
  turns an estimate into a certainty.

([WMO-No. 306, _Manual on Codes_, Vol. I.1 Part A, FM 15 METAR, regulations 15.3.1–15.3.2](https://www.eoas.ubc.ca/courses/atsc303/Instruments/wmo_guides/wmo_306-vI1_en-2013.pdf);
[ICAO PANS-AIM (Doc 10066), 1st ed. 2018, Appendix 3 §5 Item B) and §6 Item C), consolidated copy](https://www.bazl.admin.ch/dam/de/sd-web/a5B1dV8TNhUW/10066_cons_en.pdf);
[EUROCONTROL OPADD Edition 4.1, §2.3.16 Item B) and §2.3.17 Item C), ICAO APAC-hosted copy](<https://www.icao.int/sites/default/files/sp-files/APAC/Documents/EUROCONTROL%20Operating%20Procedures%20for%20AIS%20Dynamic%20Data%20(OPADD)%20Edition%204.1.pdf>),
the multinational peer)

  `{ kind: "instant"; instant: string; estimated: boolean } | { kind: "permanent" }`.

  story comes after it and adds its functions to them.

### How `parseMetarTime` chooses the month

Two candidates are found in UTC: the latest instant at or before the reference with the stated
day, hour and minute, and the earliest one after it. A month that does not have the day (`31` in
June) is skipped, so a candidate may be two months away. The result is the nearer of the two in
exact time; of two equally near, the earlier.

### What returns the sentinel

- `parseMetarTime`: a value that is not seven characters, six digits then `Z`; a day outside 01–31,
  an hour outside 00–23 or a minute outside 00–59; a reference that is not an ISO 8601 instant with
  `Z` or an offset.
- `parseNotamValidity`: a value that is not ten digits, ten digits then `EST`, or `PERM`; a space
  before `EST`; a month, day, hour or minute out of range, including hour `24`; no `yearWindow`.

## Tool

**Report Time Resolver** (`/tools/report-time-resolver/`). Section 1 takes a METAR, SPECI or TAF time
group and a reference instant, and draws a strip of seven slots, k = -3 to +3, anchored on the base
reference's answer. The chosen candidate is marked. A slider moves the reference within one month
either way, so the answer changes as it crosses a month end. Section 2 reads a NOTAM item B) and
item C) and shows the instant, an estimate or a permanent NOTAM. It calls `parseMetarTime`,
`isValidMetarTime`, `parseNotamValidity` and `isValidNotamValidity`. The strip is built from
existing calls, `addUtc` with `overflow: "reject"` for each slot and with `"constrain"` for the
reason a slot is a gap, and the library has no function for it. Teaches: a time with no month needs
a reference, and `PERM` is not a date.

## Design notes

- **The reference is required.** Defaulting it to now makes a stored report parse differently each
  month, and the reader of an archive has the receipt time, not now. The caller passes it.
- **Nearest, in exact time.** The two candidates are compared by the time between each and the
  reference, with the arithmetic behind `spanNs`, so a report made just after the reference (a clock
  slightly ahead, a reference taken a moment early) is read as well as one made before. Months are
  counted in UTC because the group is UTC.
- **`PERM` and `EST` are states, not dates.** `PERM` returns `{ kind: "permanent" }` with no instant.
  `EST` keeps its instant and sets `estimated`, so "in force" checks can treat the end as uncertain.
- **The two-digit year is the caller's.** A NOTAM's `YY` names no century, so the caller states
  `yearWindow`, as INT-15's pattern parsers require. A live feed passes `"rolling"`; an archive
  passes a fixed start year.
- **B) and C) share a reader.** Item B) is ten digits, which C) also allows, so one function reads
  both. `PERM` and `EST` belong to C) only (PANS-AIM App 3 §6); a caller reading B) treats a
  `"permanent"` result or `estimated: true` as malformed.
- **The validators take what the parsers take.** `isValidMetarTime` needs the reference because
  `parseMetarTime` does, and the two must agree on every input, a bad reference included.
  `isValidNotamValidity` needs the window because a NOTAM's day exists only in the year the window
  gives. A caller checking item B) treats `PERM` and `EST` as malformed, as with the parser.
- **`2400` is not read.** PANS-AIM writes the end of a day as `2359` ("do not use '2400'") and the start
  as `0000`, and Temporal has no hour 24.
- Item D) schedules, TAF validity periods and change groups are not part of this story.

## Corrections

The first draft of this epic described `notamTimestamp` as parsing `DDHHMM` — "`251200` = 25th day,
12:00 UTC". That is the METAR format, not the NOTAM one: items B) and C) are ten-digit `YYMMDDHHMM`,
plus `EST` and `PERM`, which that draft did not handle. The two forms are read by separate functions
here because only one of them needs a reference (overview, Corrections table).

## Authority — what each rule rests on

WMO publishes the METAR code form; the NOTAM format is ICAO's, in PANS-AIM Appendix 3, and is
cited first. EUROCONTROL's OPADD is the multinational operating procedure that applies it, cited
as a labelled peer only for what ICAO does not say. PANS-AIM was read in the consolidated copy the
Swiss Federal Office of Civil Aviation publishes, and OPADD in the copy ICAO's Asia and Pacific
office publishes.

| Item B): ten digits, year, month, day, hour, minute, in UTC | PANS-AIM App 3 §5: "For date-time group use a ten-figure group, giving year, month, day, hours and minutes in UTC" |

  this story extends
- `spanNs` from CORE-2 — the exact time between each candidate and the reference; the parser
  uses the arithmetic behind it directly, since a public function never calls another
- `TwoDigitYearOptions`, `internal/twoDigitYear.ts` and `internal/yearWindowStart.ts` from INT-15 —
  the caller-stated window for a NOTAM's two-digit year

## Decisions

- **`PERM` without `yearWindow` returns `null`.** A missing window fails on the first value, not
  only on the first dated one.
- **A METAR result has no distance limit.** The nearest candidate is at most about 31 days away;
  the caller checks staleness with `spanNs`.
- **Nothing is corrected.** `2400`, `WIE` and `UFN` return `null`. OPADD Ch. 3 gives their
  correction to a NOTAM Processing Unit, not to a reader.
- **The distance uses the core, not `spanNs`.** A public function never calls another, so
  `parseMetarTime` runs the arithmetic behind `spanNs` on `parseInstantNanoseconds`.
- **The Report Time Resolver's strip has no library function.** The library holds exactly the four
  functions and `NotamValidity`. The strip shows seven slots because an answer can sit two months
  from its reference: for `2025-03-01T00:00:00Z` and `311200Z` it is 31 January.
- **The tool's own rules are in [built.md](../../dox/built.md)** under the Report Time Resolver.

## Verification

- `parseMetarTime('251200Z', '2024-06-25T12:20:00Z')` returns `2024-06-25T12:00:00Z`
- `parseMetarTime('302350Z', '2024-07-01T00:05:00Z')` returns `2024-06-30T23:50:00Z`, the previous month
- `parseMetarTime('312350Z', '2024-07-01T00:05:00Z')` returns `2024-05-31T23:50:00Z`: June has no 31st, so the candidates are 31 May and 31 July, and May is nearer by 23 h 30 min
- `parseMetarTime('312350Z', '2025-01-01T00:05:00Z')` returns `2024-12-31T23:50:00Z`, across a year boundary
- `parseMetarTime('010010Z', '2024-06-30T23:55:00Z')` returns `2024-07-01T00:10:00Z`, the next month
- `parseMetarTime('251200', …)`, `'251200 Z'`, `'321200Z'`, `'252400Z'` and a reference with no offset return the sentinel
- `parseNotamValidity('2506151200', { yearWindow: 2000 })` returns `{ kind: 'instant', instant: '2025-06-15T12:00:00Z', estimated: false }`
- `parseNotamValidity('1407031230EST', { yearWindow: 2000 })` (OPADD's example) returns `estimated: true`; `'1407031230 EST'` returns the sentinel
- `parseNotamValidity('PERM', { yearWindow: 2000 })` returns `{ kind: 'permanent' }`, not a timestamp
- `parseNotamValidity('2506152400', …)`, `'2502301200'` and `'2506151200'` with no `yearWindow` return the sentinel
- `isValidMetarTime('302350Z', '2024-07-01T00:05:00Z')` is `true`; `'321200Z'`, `'251200'` and a reference with no offset are `false`
- `isValidNotamValidity('1407031230EST', { yearWindow: 2000 })` and `isValidNotamValidity('PERM', { yearWindow: 2000 })` are `true`; `'1407031230 EST'`, `'2502301200'` and a missing `yearWindow` are `false`
- Each validator agrees with its parser on every parse row above; a number and `null` are `false`
- `pnpm run validate` stays green

# CORE-76 — Core: Hours of work — a duty-log engine

**Scope:** Every hours-of-work rule the epic's realms run — driver, seafarer, rail crew, flight crew, resident — evaluated as composable rule objects over one duty log, with every number the caller's.

## Gap

Five realms keep a status log (off, rest, driving, on duty, flight, call, …) and test it against rules of about a dozen shapes: a cumulative cap since a reset; an elapsed window that rest inside it does not extend; a required interruption after N cumulative hours, sometimes as an ordered split; rolling caps over elapsed hours, operator-designated days or local calendar periods; caps over adjacent fixed weeks and averages over several; quotas of reduced rests; "due by the end of N periods"; N-of-M patterns; paired rests excluded from a window; caller-declared extensions; lookback exclusions; composite off-duty periods; counters keyed by the date a period starts; a free period of Z hours inside every rolling Y-hour window that contains n local nights; pre-duty rest as the larger of k × the preceding duty and a floor. Strip the numbers and the shapes are identical across every regime; only the numbers differ, and the numbers are the caller's. Eight one-body stories were the same engine each time (painpoints, "One duty-log shape, five regulators"; "Road — zero coverage").

The two facts every hand-built implementation gets wrong are generic too. The day is operator-designated: a start time in a reference zone, not the local midnight where the person happens to be. And a "24-hour period" in a rule is every sliding 24-hour window unless the rule names a fixed period, so a check that buckets by calendar day passes logs that a sliding window fails.

## Scope

- `packages/gmt/src/types/duty.ts`:
  - `DutyEntry<S extends string = string>` is `{ status: S, start: string, end: string }` — instants; `S` is the caller's status vocabulary.
  - `DutyDay` is `{ timeZone: string, dayStartTime: string, disambiguation?: Disambiguation }` — the operator-designated day; neither the zone nor the start time has a default, and `disambiguation` is `"compatible"` when absent, as in `resolveLocal`.
  - `Period` is `{ elapsed: string } | { operatorDays: number } | { calendarDays: number } | { calendarMonths: number } | { calendarYears: number } | { isoWeeks: number }` — an elapsed duration, or a count of local periods in the reference zone.
  - `Reset<S>` is `{ statuses: S[], consecutive: string }` — a run of at least `consecutive` in any of `statuses` resets a counter.
  - `PairSpec` is `{ eachAtLeast: string, oneAtLeast: string, combinedAtLeast: string }` — a paired rest is two periods that satisfy all three.
  - `DutyRule<S>` — the discriminated union in the table below; every member carries `{ label: string, severity?: 'violation' | 'advisory' }` and `severity` defaults to `'violation'`.
  - `RestPair` is `{ first: Interval, second: Interval }` — a paired rest, as `qualifyingRestPairs` returns it.
  - `RuleOutcome` is `{ label: string, kind: DutyRule['kind'], severity, satisfied: boolean, used: string | number | null, limit: string | number | null, remaining: string | number | null, window: Interval | null, periodBasis: 'elapsed' | 'operatorDay' | 'calendar' | null, dueBy: string | null, resetAt: string | null }`.
  - `DutyReport` is `{ at: string, outcomes: RuleOutcome[], violations: RuleOutcome[], advisories: RuleOutcome[] }`.
  - `DutyViolation` is `{ label: string, window: Interval, used: string | number, limit: string | number }`.
- `packages/gmt/src/workforce/calculate/dutyDayFor.ts`:
  - `dutyDayFor(instant: string, day: DutyDay): Interval | null` — The operator-designated 24-hour period an instant falls in: the most recent `dayStartTime` in `timeZone` at or before the instant, to the next one. A `dayStartTime` that is nonexistent or ambiguous on a transition day resolves under `day.disambiguation`, `'compatible'` by default (the CORE-4 policy), stated in the JSDoc with the [LOCAL_TIME_RESOLUTION.md](../../reference/LOCAL_TIME_RESOLUTION.md) vocabulary; the period is then 23 or 25 hours long and the JSDoc says so.
- `packages/gmt/src/workforce/calculate/evaluateDutyLog.ts`:
  - `evaluateDutyLog(log: DutyEntry[], at: string, rules: DutyRule[], options: { timeZone: string, dayStartTime?: string, disambiguation?: Disambiguation }): DutyReport | null` — Every rule evaluated at one instant, each reported whether or not it binds. `dayStartTime` is required by any rule whose `Period` is `operatorDays`; a rule that needs it without it returns the sentinel. A planned roster is the same call with the plan appended to the log and `at` set to the plan's end.
- `packages/gmt/src/workforce/calculate/dutyViolations.ts`:
  - `dutyViolations(log: DutyEntry[], range: Interval, rules: DutyRule[], options): DutyViolation[] | null` — Every violation inside a range, each with the window that failed it: the monthly record, not the dispatch check.
- `packages/gmt/src/workforce/calculate/dutyTotals.ts`:
  - `dutyTotals(log: DutyEntry[], window: Interval, statuses: string[]): string` — Merged, summed time in any of `statuses` inside `window`, as an ISO duration.
- `packages/gmt/src/workforce/calculate/longestRun.ts`:
  - `longestRun(log, window: Interval, statuses: string[]): { interval: Interval, duration: string } | null` — The longest unbroken stretch in `statuses` inside the window; the sentinel when there is none.
- `packages/gmt/src/workforce/calculate/qualifyingRests.ts`:
  - `qualifyingRests(log, spec: { statuses: string[], minimum: string }): Interval[]` — Rest periods of at least `minimum`.
- `packages/gmt/src/workforce/calculate/qualifyingRestPairs.ts`:
  - `qualifyingRestPairs(log, spec: { statuses: string[], minimum: string, pair: PairSpec }): RestPair[]` — The pairs of consecutive rests, each shorter than `minimum`, that satisfy all three constraints.
- `packages/gmt/src/workforce/validate/isValidDutyLog.ts`:
  - `isValidDutyLog(log: unknown): boolean` — Entries are ordered by `start`, non-overlapping, each `end` after its `start`, every bound a parseable instant, every status a string. Everything else returns the sentinel from the functions above.
- Docs site (`apps/dox/src/content/docs/`, per [../docs-site.md](../docs-site.md)):

The engine is the `workforce/` cross-industry layer (`@northguild/gmt/workforce`: `workforce/calculate/` holds the seven calculators, `workforce/validate/` holds `isValidDutyLog`). ### Rule kinds (`DutyRule.kind`), every number caller-supplied

| kind | fields | covers |
| --- | --- | --- |
| `cumulativeCap` | `statuses, cap, since: Reset` | A cap on time in `statuses` since the last reset: an 11-hour driving cap since a 10-hour off reset; a 14-hour on-duty cap |
| `elapsedWindow` | `startStatuses, length, restrictedStatuses, since: Reset, exclude?: PairSpec, extension?: { by, from }` | A window that opens when work starts and closes `length` later regardless of rest inside it; a qualifying paired rest excluded from the window; a caller-declared extension (2 hours from an instant the caller names) |
| `requiredInterruption` | `countedStatuses, after, interruption: { minimum, outsideStatuses?, orderedSplit?: string[] }` | A 30-minute interruption after 8 cumulative hours; an ordered split (15 then 30) that counts only in that order |
| `rollingCap` | `statuses, cap, window: Period, reset?: Reset, precondition?: { restStatuses, minimum, beforeHours }` | 60 hours in 7 operator days; 70 in 8; 100 hours in 672 elapsed hours; 1,000 in 365 calendar days; a cap that applies only after a stated rest inside the preceding hours |
| `fixedPeriodCap` | `statuses, cap, period: Period, adjacent?: number, average?: boolean` | 56 per ISO week; 90 over two adjacent weeks; 80 averaged over 4 weeks; per-calendar-month caps, with a tour split at the month boundary |
| `restRequirement` | `restStatuses, per: Period, minimum, composition?: { maxPeriods, longestAtLeast, othersAtLeast? }, composite?: { consecutive, additional, blockMinimum }, maxGap?` | 10 hours of rest in every sliding 24 in at most two periods, one at least 6; 8 consecutive plus 2 more in blocks of at least 30 minutes; no more than 14 hours between rests |
| `freePeriod` | `restStatuses, minimum, within: Period, containing?: { window: LocalWindow, count }, atLeast?: number` | 30 consecutive hours off within every 168; 36 hours off containing two local nights; one 24-hour free period in every seven days, on average over four weeks |
| `restBeforeDuty` | `restStatuses, minimum, within, orFactor?: { k, floor }` | 10 hours off in the 24 before a duty; rest before duty of at least the larger of k × the preceding duty and a floor |
| `quota` | `event: { statuses, minimum, maximum }, count, reset: Reset \| { every: Period }` | At most 3 reduced rests between two full rests; reduced weekly rests per period |
| `dueBy` | `event: { statuses, minimum }, within: { periods, period }, reset?` | A rest of at least N due by the end of six operator days after the last one; 48 hours off after 6 initiation days |
| `pattern` | `period, lookback, classes: { label, statuses, minimum }[], require: { label, atLeast }[]` | At least 4 rests in any 4 weeks, at least 2 of them regular; a return-within-window rule |
| `occurrenceCap` | `statuses, per: Period, lookback, maximum, byInitiationDate?: boolean` | Night duty no more often than every third night; consecutive initiation days counted by the local date a period starts |
| `usageLookback` | `uses: string[], notWithin: Period, reset: Reset` | An allowance not used within the previous N days, restored by M hours off |

Nested caps (a 13-hour cap inside a 14-hour cap inside a 16-hour window) are three rules and are reported separately.

## Design notes

- **Rules, not regimes.** A regime is an array of rule objects the caller assembles and labels; the report is keyed by those labels and never by a clause, and no rule kind carries a number of its own. The docs show five example arrays labelled by their numbers only.
- **The day is operator-designated.** `dutyDayFor` and every `operatorDays` period use `{ timeZone, dayStartTime }`; there is no default day start and local midnight is never assumed. A log whose entries cross zones still buckets by the reference zone.
- **Elapsed and calendar periods are different arithmetic.** `{ elapsed }` is exact time and ignores transitions; `{ calendarDays | calendarMonths | calendarYears | isoWeeks }` are local periods in `timeZone` and are 23 or 25 hours long on transition days; `{ operatorDays }` are `dutyDayFor` periods. Every outcome states which basis it used in `periodBasis`.
- **Sliding is the default reading of a duration.** A rule written as a `Period` of `{ elapsed: 'PT24H' }` is every sliding 24-hour window ending at `at`; only `isoWeeks`, `calendarMonths`, `calendarYears` and `fixedPeriodCap` are fixed periods. A caller who wants a fixed 24-hour period says `{ operatorDays: 1 }`.
- **Ship's time and acclimatisation are caller pre-processing.** A log kept in ship's time is converted with MAR-18's `fromShipTime` before it is evaluated; a crew member's reference zone comes from AV-27's `acclimatisedZone` or from the caller. This engine sees instants and one reference zone.
- **Statuses are the caller's strings.** `DutyEntry<S>` is generic; a third state such as deadhead-from-assignment is just another status named in the rules that count it, and a status a rule names that the log never uses is fine. A status in the log that no rule names is ignored.
- **Every rule is reported, not just the binding one**, with `used`, `limit`, `remaining`, `window`, `satisfied`, `dueBy` and `resetAt`, so a dispatcher can see the second-tightest limit before it binds. `severity: 'advisory'` outcomes list under `advisories`, never under `violations`.
- **Facts GMT cannot know are parameters.** A declared condition, a return to a location, an agreement in force, a caller-approved extension: each is a rule field (`extension`, `precondition`) or a status the caller writes into the log. The engine tests the time part only.
- **Paired rests are three constraints, not two integers.** `PairSpec` states each period's floor, the floor of the longer one and the combined floor; 7.5 + 2.5 and 8 + 2 both satisfy `{ eachAtLeast: 'PT2H', oneAtLeast: 'PT7H', combinedAtLeast: 'PT10H' }` and 6 + 4 does not.
- **Interval algebra, not loops over minutes.** Totals are `mergeIntervals` then `intersectIntervals` with the window then `sumIntervals` (CORE-6); calendar periods come from `bucketRange` (CORE-5); a tour that crosses a period boundary is cut with `splitIntervalAt` and each part counted in its own period.
- GMT reports totals, remaining time and violations. It does not decide dispatch, fitness or eligibility, and the JSDoc says the function implements no standard and takes every number from the caller.

## Decisions of record

Settled while building the story (2026-10-14). The rule types' JSDoc in `types/duty.ts` is the full statement of each kind; these are the choices the spec left open or got wrong.

- **Names and places follow the repo's rules.** `dutyDayFor` takes an instant, so it lives in `workforce/calculate/`, not `workforce/get/` (coding standards: `get/` is for current-moment readers). The validator is `isValidDutyLog`, as every validator is named, in `workforce/validate/`. One exported function per file, so `dutyViolations`, `longestRun`, `qualifyingRests` and `qualifyingRestPairs` have their own.
- **Public functions are not generic.** The reference generator refuses a generic public function (#288). The types keep `S extends string = string`, so a typed status vocabulary still passes in; the functions take `DutyEntry[]` and `DutyRule[]`.
- **`qualifyingRests` is two functions.** One returns `Interval[]`, `qualifyingRestPairs` returns `RestPair[]`, rather than one function whose return type depends on an option. A pair is two rests in a row, each shorter than `minimum` (a rest of `minimum` is a full rest and pairs with nothing; no pair spans one), and a rest shorter than `eachAtLeast` is skipped. `elapsedWindow`'s `exclude` uses the same pairs.
- **`elapsedWindow` takes `since: Reset`, and `rollingCap` takes `reset?: Reset`.** The table omitted them, but the window cannot open without knowing what reset precedes it, and the verification's 34-hour restart needs a reset on the rolling cap.
- **`fixedPeriodCap.buckets` is not built.** A rule has one cap and one outcome, so several buckets in one rule would have to be folded into one number. A cap per status group is a rule per group, reported separately, as nested caps are.
- **The verification's 671 was wrong.** 28 local days across a fall-back are 673 hours; across a spring-forward, 671. Both are asserted.
- **Every function that resolves a wall time takes `disambiguation`**, as CORE-55 decided under the LOCAL_TIME_RESOLUTION binding rule, which names a duty limit as a case for `"reject"`. `DutyDay` and the options of `evaluateDutyLog` and `dutyViolations` take it; the default is `"compatible"`, the policy the spec names. It covers operator-day starts and `freePeriod` window edges; calendar days, weeks, months and years are real boundaries and ignore it. `"reject"` returns the sentinel only for a day that starts or ends at a repeated or skipped time, or a window edge that reaches a free run.
- **`dutyViolations` returns `null` on invalid input, not `[]`.** As the spec gives it. An empty record must not be mistaken for a refused call.
- **How the log is read.** Up to `at`: later entries are ignored and one straddling `at` is cut. Time no entry covers is in no status, so an unlogged gap is neither work nor rest and ends a run. A run is touching entries in the rule's statuses, merged with the CORE-6 internal (`coalesceIntervalNanoseconds`).
- **Which period is current.** Counts of local periods end with the one holding the last instant before `at`. At a boundary the period just ended is judged, so a roster whose `at` is its end is checked through its last day, and `dutyViolations` evaluates the same way.
- **A window not yet over has not failed a minimum** while it could still be met: with rest from `at` to its end (`restRequirement`, `freePeriod`), or with enough runs still able to start before it ends, each `minimum` long before the next (`pattern`, whose runs count where they start). A cap fails as soon as it is passed.
- **Counting.** A free period is counted as `floor(length / minimum)` per run (a 48-hour run holds two 24-hour free periods); with `containing`, greedily, earliest end first. `quota`, `pattern` and `occurrenceCap` with `byInitiationDate` count a run in the period it starts in, measured whole. `quota` does not count a run the log carries on past `at`, since it may still grow past `maximum`.
- **Durations and counts are exact.** Hours, minutes, seconds and days of 24 hours; years, months and weeks are refused, as `exactDurationNanoseconds` refuses them. Every cap, length and floor is positive. A count of local periods is 1 to 10,000, including a period repeated by `adjacent`, `lookback` or `dueBy`'s `periods`, and so is `containing.count`. `fixedPeriodCap.period` and `occurrenceCap.per` are typed `LocalPeriod`, since an `elapsed` one is refused. A count GMT reports is exact or refused: a count of free periods past `Number.MAX_SAFE_INTEGER` returns the sentinel.
- **`orFactor`'s `k` is the shortest decimal `String(k)` prints, read exactly.** `1.1` is 11/10 and `0.1 + 0.2` is 0.30000000000000004; the product is taken in bigint and rounded up to the nanosecond. A requirement past the longest duration Temporal holds returns the sentinel.
- **`dueBy`.** The clock starts at the end of the last qualifying rest (or a `reset`, when later). The rest is due by the end of the `periods`-th period, the period the clock starts in counting as the first, and it must start by then: a rest begun by `dueBy` and still going holds.
- **`usageLookback` counts uses at or before `at`**, inside `notWithin`, after the last reset. More than one is a violation; `remaining` is 1 when the allowance is free. Each window holds a use once: a window of local periods holds only its own uses, so a use exactly on its end is the next window's, and an `elapsed` window runs from just after `at − length` up to and including `at`, so two uses exactly `length` apart pass.
- **`restBeforeDuty`.** A duty starts where logged time outside `restStatuses` begins, and a stint after any rest is a new duty start. GMT cannot tell a break from a short rest without a threshold the rule does not have, so a caller logs a break inside a duty in a status outside `restStatuses`; a "shorter than X is a break" field is left for a later story if a regime needs it.
  - Without `orFactor`, the rest before a duty is the longest rest inside `within` before its start, so a short break between two stints does not stand in for the rest before them.
  - With `orFactor`, the rest is the run that ends where the duty starts, measured whole, and the requirement is the largest of `minimum`, `floor` and `k` × the duty that rest ends. That duty runs from the end of the last rest of at least `minimum` before it to where the rest starts, breaks included. So every duty is judged against the rest right after it, and logging more of the time before a duty as rest never fails it, unless a whole duty becomes rest: the rests around it are then one, which ends the duty before it. A seeded property test asserts this. The record does not judge a rest that starts with the log, since it may have begun before.
- **`elapsedWindow`'s paired rest.** The window's time stops while the second rest of a pair lasts, so a second rest that starts before the close moves it by its whole length, and one that starts after the close moves nothing: the window had closed. A rest shorter than `eachAtLeast` between the two halves is neither half of the pair nor a break in it.
- **`restRequirement`'s `maxGap` measures the work before the first rest.** The log's first entry starts a stretch without rest, as the end of a rest would. Both functions read it so: in `dutyViolations` only windows that start inside the log are judged, so the stretch is logged time.
- **`dutyViolations` checks every instant where a rule's answer can change.** Entry bounds; those bounds shifted by a sliding window's length; where a run reaches, or in a sliding window falls below, a floor the rule compares it with; where two rests cross as the longest; where the second rest of a pair completes the combined floor against the partner `restPairs` gives it; where a gap passes `maxGap`, a rest falls due or a free period gains or loses a local window; the boundaries of local periods; and the instants either side of each. A rule's measures are piecewise linear in the instant, so this finds every failed window, and the record does not change when a status is split into two entries. Two seeded property tests assert it: one cuts a twelve-day log once, the other cuts every entry of a four-day log.
- **One entry per violation.** A moving window (an elapsed duration, or more than one local period) is one violation while it keeps failing with no passing check between, reported by its worst window, the earliest on a tie; a rolling count of days therefore lists a new violation each time the cap is broken again after a pass. A count since a reset, or one short rest before a duty, is one violation however often it is checked, reported by its worst check. One fixed period is one violation, reported by its last check, which judges the period complete: its checks can fail on different floors (the rest so far, the gap), so the worst is not one measure. Advisories are not listed.
- **A violation is listed in the range it began in.** One already failing at `range.start` belongs to the range before; one still failing at `range.end` is followed to its worst window, which may end after the range, up to the log's last entry. Two adjacent ranges list every violation once.
- **The record only grows.** Each check reads the log as it stood then, so a failure stays listed when a later rest would have excused it, such as one that completes a pair after the window it would have moved closed. The record lists what a check at that moment would have said.
- **Time after the log's last entry.** `dutyViolations` checks nothing after the last entry, so a range running past the log (a month to date) reads as one ending with it, and a period still open there is judged as not yet over. `evaluateDutyLog` reads it as no status, as it reads any unlogged time.
- **Time before the log's first entry.** `evaluateDutyLog`, the check before dispatch, reads it as no status, so a rest rule fails for want of logged rest; the caller gives enough history. `dutyViolations`, the record, checks nothing before the rule's first evidence (the log's first entry, or for `usageLookback` its first use), and does not judge a rest rule (`restRequirement`, `freePeriod`, `pattern`, `restBeforeDuty`) on a window that starts before the first entry, since the log cannot say what happened then. A cap is judged, since unlogged time never counts towards one. `dutyViolations`'s JSDoc states both readings side by side.
- **A record's work is bounded by the log, not the range.** Period boundaries are walked only over the time the log covers, so a 40-year range over a week of log reads as that week. More than 10,000 of a rule's periods ending there is refused; a span of 10,001 periods of 8 days or more (14 for a week, 38 for a month, 373 for a year, each longer than any period lasts) is refused without walking. One rule needing more than 1,000,000 instants checked is refused. A free period's multiples are taken only up to `atLeast + 1` and inside the range, since a run's count past `atLeast` changes no answer.
- **Local windows and runs are found once per call.** A `freePeriod`'s `containing` windows are resolved around the rests a request reaches, kept in stretches of dates, and a request far from every stretch starts its own, so the dates between two far-apart rests are never resolved. One run of rest may hold at most 20,000 of them (about 54 years of a daily window); counting the free periods in a longer one exactly would need every window, so it returns the sentinel. The runs of rest are found once per call and binary-searched to each window.
- **Periods are walked once per call, and jumped across where no clock changes.** The period k after another is found by stepping through a few cached periods, by a jump for weeks, months and years where no transition lies between (each such unit is then one period, so the period k later holds the wall clock k units after the first one's middle), and otherwise by a walk the scale keeps, so a record walks each period once. Across a transition the periods are walked, since a clock change can open a period of its own: Goose Bay's fall-back at 00:01 on 7 November 2010 reopened 6 November for a 59-minute day, and its 2009 fall-back reopened 31 October for a 59-minute month, as coding standards § Calendar & zone semantics says. A day is always walked, since a deleted date has no period.
- **"An unknown status in a rule"** in the verification is a status that is not a string, or an empty status list: both return the sentinel. A status the log never uses is fine, as the design notes say.

## Corrections

- Eight realm stories — four over road driver hours, one over seafarer rest, one over rail-crew hours, one over cumulative flight-crew limits, one over resident work hours — each specced one body's numbers as a status function named for that body or its jurisdiction (three driver-status functions, `restHoursStatus`, a rail-hours status, `cumulativeLimits`, a resident-hours status, and their companions). Each was this engine with a regime's constants and clause citations inside it. They are absorbed here, the constants are the caller's, and no clause is named anywhere (tracker, "GMT tracks no law").
- Their sound findings survive as rule kinds: the operator-designated day; a fixed week versus a rolling window; an ordered split break; paired rests defined by three constraints, not integers; a precondition on a rolling cap; caps per local calendar month with tours split at the boundary; consecutive days counted by the date a period starts; "must" versus "should" as `severity`.
- `DutyEntry` was `{ status: 'off' | 'sleeper' | 'driving' | 'onDuty' | … }` with a different union per regime; it is generic over the caller's status strings.
- The road realm's only content was those numbers, so the realm is gone from the tracker; its examples live on this story's guide, labelled by numbers.

## What gmt provides (do not re-implement)

- `mergeIntervals` / `subtractIntervals` / `sumIntervals` / `intersectIntervals` / `splitIntervalAt` from CORE-6 — the algebra under every total, window and boundary split
- `bucketRange` / `floorToZone` / `getIsoWeekDate` from CORE-5 — local calendar periods and ISO weeks in the reference zone
- `resolveLocal` / `classifyLocal` from CORE-4 — the day start on a transition day
- `spanMs` from CORE-2 — elapsed windows and `remaining`

## Verification

One row per rule kind, number-labelled, and an example array each for a driver, a seafarer, a rail crew, a flight crew and a resident, every result checked against the built package:

- `cumulativeCap`: an 11-hour cap on `driving` since a 10-hour `off` reset reports `remaining: 'PT0S'` at exactly 11 hours and a violation at 11:01; a 9:59 off period does not reset it and a 10:00 one does
- `elapsedWindow`: a 14-hour window is not extended by a 2-hour `off` break inside it; with `exclude: { eachAtLeast: 'PT2H', oneAtLeast: 'PT7H', combinedAtLeast: 'PT10H' }` the window is recalculated from the end of the first period of a qualifying pair, 7.5 + 2.5 qualifies and 6 + 4 does not; `extension: { by: 'PT2H', from }` moves the close by two hours from the instant the caller names and not otherwise
- `requiredInterruption`: after 8 cumulative hours, 30 minutes in any status outside the counted set satisfies it; `orderedSplit: ['PT15M', 'PT30M']` is satisfied by 15-then-30 and not by 30-then-15

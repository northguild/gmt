# CORE-108 — Core: Move GMT onto `temporal-polyfill`

**Scope:** `packages/gmt` depends on `temporal-polyfill` instead of `@js-temporal/polyfill`. The
workarounds the new polyfill does not need are removed, the weekly swap job becomes an upgrade
check, and Dox `/bundle-size` compares the two polyfills. Adds no function. Tracked as #460.

## Gap

The polyfill is the floor of every GMT bundle: importing one function ships all of it.
`@js-temporal/polyfill` 0.5.1 is 44.2 kB gzipped on its own, and `temporal-polyfill` 1.0.8 is
23.3 kB (#460 has the full table). Most of `internal/temporalCompat/` exists for
`@js-temporal/polyfill` defects.

On the CORE-92 swap check for 1.0.8, Node passes all 71,340 tests and Chromium has no swap-only
failure. Firefox and WebKit each have one: the D9 row in `largeMonthArithmetic.test.ts`, where
`addZoned` on a non-ISO calendar with `{ months: 4294967295 }` returns the right value but takes
1.2–1.4 s against the 1,000 ms limit. 1.0.8 does in-range month arithmetic in bounded time but is
slow to throw `RangeError` on an out-of-range month amount, and GMT's zoned non-ISO path reaches
that call. The offset sweep finds 0 zones that differ from `Intl.DateTimeFormat` in 418 zones.

## Scope

1. **Range check first.** GMT rejects a month amount past Temporal's range before it calls the
   polyfill, so the D9 rows stay inside their limit on every leg. D9 stays, its trigger pointing
   at `temporal-polyfill`.
2. **The seam.** `src/internal/temporal.ts` imports `temporal-polyfill/full/implementation` and stays
   the only file that names the implementation. The ambient module in `src/test/hostModules.d.ts`
   goes, so the package's own types apply.
3. **Types.** The type errors the new declarations raise in `packages/gmt` are fixed in the source.
4. **Workarounds.** Each `temporalCompat` group is judged on `temporal-polyfill` by its canary, on
   Node and in the browsers it targets. One no longer needed is removed with its sentinel and
   README entry; one still needed stays, its trigger pointing at the `temporal-polyfill` behaviour.
5. **CI.** The weekly swap job becomes an upgrade check: the newest `temporal-polyfill` release
   against the pinned version, on Node and in all three browsers.
6. **Lint plugins.** `gmt-oxlint`, `gmt-eslint` and `gmt-biome` name `temporal-polyfill` wherever
   they name the polyfill today.
7. **Bundle size.** Budgets are set from the new measured sizes. `/bundle-size` gains a section on
   the move with charts comparing the two polyfills, `temporal-polyfill` in green and
   `@js-temporal/polyfill` in orange. Both sets of figures are generated by
   `scripts/bundle-size.mjs`, never typed in.
8. **Docs.** The `/upstream/` "Why this polyfill" section, the guides and the generated reference
   describe `temporal-polyfill`. Every filing on both polyfill repos stays listed.
9. **READMEs and a changeset** describe the change.

Out of scope: native Node 26 `normalizeDuration` (#440), which is native Temporal only.

## What gmt provides (do not re-implement)

- CORE-92: the swap job in `.github/workflows/temporal-oracle.yml` and `scripts/polyfill-swap.mjs`
- `node scripts/temporal-compat.mjs check` and the workaround canaries
- `scripts/bundle-size.mjs` and `apps/dox/src/generated/bundle-size.json`

## Verification

- The whole `packages/gmt` suite passes on Node and in Playwright Chromium, Firefox and WebKit.
- `node scripts/temporal-compat.mjs check` passes.
- `pnpm run validate` stays green.

## Decisions

1. Work starts on `temporal-polyfill` 1.0.8 although Firefox and WebKit each fail the one D9 row.
   The range check in Scope 1 fixes it in GMT, and Verification still needs all four legs green.

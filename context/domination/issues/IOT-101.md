# IOT-101 — IoT: PTP time

**Scope:** Convert between a Precision Time Protocol timestamp, which counts TAI, and a UTC instant, using the UTC offset the caller's grandmaster announces.

## Gap

PTP shares its epoch value with Unix time and counts a different time scale. "The PTP epoch is
1 January 1970 00:00:00 TAI", and the timestamp "is not affected by leap seconds". To get UTC, a
receiver subtracts the `currentUtcOffset` the grandmaster announces — 37 seconds since 2017.
Skipping it gives a silent 37-second error, a documented, recurring failure in lidar, industrial
and broadcast deployments ([painpoints § IoT and continuous time](../painpoints.md#iot-and-continuous-time)).
Sensor data then sits 37 seconds away from every other clock in the system, and nothing raises an
error.

([RFC 8877 §4.3, the PTP timestamp format](https://www.rfc-editor.org/rfc/rfc8877#section-4.3);
[RFC 8575, the IEEE 1588 YANG module, `time-properties-ds`](https://www.rfc-editor.org/rfc/rfc8575);
IEC/IEEE 61588:2021, the international edition of IEEE 1588 — not reached; marked, not asserted)

## Scope

- `packages/gmt/src/iot/convert/ptpToUtc.ts`:
  - `ptpToUtc(timestamp: PtpTimestamp, currentUtcOffset: number): string` — A PTP timestamp to a UTC
    instant ending in `Z`. `currentUtcOffset` is required, with no default.
- `packages/gmt/src/iot/convert/utcToPtp.ts`:
  - `utcToPtp(value: string, currentUtcOffset: number): PtpTimestamp | null` — The inverse.
- `packages/gmt/src/types/ptp.ts` — `PtpTimestamp`: `{ seconds: bigint; nanoseconds: number }`.
  `ptpToUtc` also takes `seconds` as a safe-integer `number`, as `fromProtoTimestamp` does, because
  a 48-bit count fits one; `utcToPtp` always returns a `bigint`.
- This story opens the `iot/` realm: the `@northguild/gmt/iot` and `@northguild/gmt/iot/convert`
  subpaths (`package.json` `exports` and `typesVersions`, the dox `gmt-modules.ts` barrel), and the
  IoT industry in `apps/dox/src/data/industries.json`, with namespace `iot`, drawing on `timescale`
  and `precision`.

### The arithmetic

`ptpToUtc` returns the instant `seconds + nanoseconds × 10⁻⁹ − currentUtcOffset` seconds after
1970-01-01T00:00:00Z, read on the UTC count every other GMT instant uses. `utcToPtp` adds the offset
back.

### What returns the sentinel

- `ptpToUtc`: `seconds` below 0 or at or above 2⁴⁸; a `number` `seconds` that is not a safe integer;
  `nanoseconds` that is not an integer from 0 to 999 999 999; a `currentUtcOffset` that is not an
  integer from −32 768 to 32 767; a result before 1970-01-01T00:00:00Z or outside Temporal's range;
  a missing member.
- `utcToPtp`: a value that is not an ISO 8601 instant with `Z` or an offset; a second of `60`; the
  same offset rule; a result outside 0 to 2⁴⁸ − 1 seconds.

## Tool

**PTP Clock Converter.** Enter PTP seconds and nanoseconds and the announced `currentUtcOffset` and
see the UTC instant, the reading with the offset ignored, and whether the announced offset matches
TAI − UTC from the leap-second table for that instant. Calls `ptpToUtc`, `utcToPtp` and
`taiMinusUtc`. Teaches: PTP counts TAI, and the offset is a fact the grandmaster announces, which can
be wrong.

## Design notes

- **`currentUtcOffset` is required and has no default.** A default of 37 is wrong for any system
  whose grandmaster announces something else, and would hide the misconfiguration this function
  exists to expose. The caller reads it from the Announce message's time properties.
- **The function applies the announced offset; it does not consult the table.** A receiver converts
  with the offset its grandmaster announces, and reproducing the receiver's reading is the point.
  Converting through the leap-second table is what `fromTAI` (MAR-16) does. A caller who wants to
  check the grandmaster compares `currentUtcOffset` with `taiMinusUtc` (SPA-48) for the result's
  date; the Tool shows that comparison. No separate check function is added.
- **The offset means something only on the PTP time scale.** RFC 8575 describes it as "The offset
  between TAI and UTC when the epoch of the PTP system is the PTP epoch … i.e., when ptp-timescale
  is TRUE; otherwise, the value has no meaning". A grandmaster on the arbitrary time scale (ARB) has
  no epoch the function can read; the JSDoc says so, and the caller does not call it.
- **A leap second is not written.** With one offset for the whole call, a UTC second of `60` has no
  reading of its own, so `utcToPtp` returns the sentinel for one; `ptpToUtc` never writes one. During
  an insertion the grandmaster announces the new offset, and the caller passes it.
- **Field sizes are the wire's.** The PTP timestamp is 80 bits: 48 of seconds and 32 of nanoseconds,
  "in the range 0 to (10^(9))-1". The offset is a 16-bit signed integer.
- gPTP (IEEE 802.1AS) uses the same time scale and the same trap; its text was not reached either.

## Authority — what each rule rests on

IEC/IEEE 61588 is the international edition of IEEE 1588. Its text is sold and was not reached; the
IETF documents below restate the facts this story needs and are the citations.

| Rule | Source |
| --- | --- |
| The PTP epoch is 1970-01-01T00:00:00 TAI, unaffected by leap seconds | RFC 8877 §4.3: "The PTP [IEEE1588] epoch is 1 January 1970 00:00:00 TAI"; "This timestamp format is not affected by leap seconds" |
| 80-bit timestamp: 48 bits of seconds, 32 of nanoseconds in 0 to 10⁹ − 1 | RFC 8877 §4.3: "PTP [IEEE1588] uses an 80-bit timestamp format"; the truncated form "is the 64 least significant bits", with nanoseconds "in the range 0 to (10^(9))-1" |
| `currentUtcOffset` is TAI − UTC in seconds, a signed 16-bit integer, meaningful only on the PTP time scale | RFC 8575, `time-properties-ds`, leaf `current-utc-offset`, type `int16`, with the description quoted above; the module references IEEE 1588-2008 §8.2.4 |
| The IEEE 1588 clauses themselves | IEC/IEEE 61588:2021 — **not reached; marked, not asserted** |
| No default offset | **GMT rule.** A number from the caller's grandmaster, not a constant |
| A UTC second of `60` is refused by `utcToPtp` | **GMT rule.** One offset per call gives an inserted second no reading of its own |
| Sentinels | [coding-standards § API Contract](../../coding-standards.md#api-contract) |

## What gmt provides (do not re-implement)

- `toNanoseconds` / `fromNanoseconds` from CORE-1 — the nanosecond count behind both directions
- `taiMinusUtc` from SPA-48 — TAI − UTC by date, which the Tool compares with the announced offset
- `toTAI` / `fromTAI` from MAR-16 — the table-based TAI conversion, the other answer the guide shows

## Verification

- `ptpToUtc({ seconds: 1704067237n, nanoseconds: 0 }, 37)` returns `2024-01-01T00:00:00Z`; with an offset of `0` it returns `2024-01-01T00:00:37Z`, the 37-second error, asserted
- `ptpToUtc({ seconds: 1704067237, nanoseconds: 500000000 }, 37)` returns `2024-01-01T00:00:00.5Z`
- Round-trip: `utcToPtp(ptpToUtc(t, 37), 37)` returns `t` for timestamps with 0, 1 and 999 999 999 nanoseconds
- `utcToPtp('2024-01-01T02:00:00+02:00', 37)` returns `{ seconds: 1704067237n, nanoseconds: 0 }`
- The Tool's check flags a grandmaster still announcing `36`, the value until the end of 2016: `taiMinusUtc('2024-01-01T00:00:00Z')` is `37`, and `ptpToUtc` with `36` returns `2024-01-01T00:00:01Z`
- `nanoseconds` of `-1` or `1000000000`, `seconds` of `-1n` or `2n ** 48n`, an offset of `37.5` or `40000`, and a missing `nanoseconds` member return the sentinel
- `ptpToUtc({ seconds: 0n, nanoseconds: 0 }, 37)` returns the sentinel: the result is before 1970
- `utcToPtp('2016-12-31T23:59:60Z', 37)` and `utcToPtp('2024-01-01T00:00:00', 37)` return the sentinel
- Calling either function without `currentUtcOffset` is a type error, and returns the sentinel at run time
- `pnpm run validate` stays green

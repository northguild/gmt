# MAR-17 — Maritime: AIS timestamp reconstruction

**Scope:** Reconstruct full timestamps from AIS position reports, which carry only a second-of-minute.

## Gap

An AIS Class A position report (messages 1, 2, 3) does not carry a date or even an hour. It carries a **6-bit second-of-UTC field** — the UTC second at which the position was generated by the electronic position fixing system — plus four reserved values that signal the fix quality rather than a time. Reconstructing a usable timestamp requires a reference instant from the receiver, and mishandling the reserved values silently produces positions timestamped at second 60 through 63.

## Scope

- `packages/gmt/src/maritime/parse/aisSecondOfUtc.ts`:
  - `parseAisSecondOfUtc(second: number, receivedAt: string): { instant: string, quality: AisTimeQuality } | null` — Reconstructs the report instant by aligning `second` to the nearest minute boundary around `receivedAt`.
  - `classifyAisSecond(second: number): AisTimeQuality` — Classifies the raw field without reconstructing.
- `packages/gmt/src/maritime/parse/aisBaseStationTime.ts`:
  - `parseAisBaseStationTime(fields: { year: number, month: number, day: number, hour: number, minute: number, second: number }): string` — AIS message 4 (base station report) carries a full UTC date and time; this is the only AIS message that does.
- `packages/gmt/src/maritime/format/navTimestamp.ts`:
  - `navTimestamp(isoString: string): string` — Navigation-format timestamp: ISO 8601 UTC with a `Z` suffix and second precision.

## AIS second-of-UTC field

| Value | Meaning |
| --- | --- |
| 0–59 | Valid UTC second of the position fix |
| 60 | Time stamp not available (the default) |
| 61 | Positioning system in manual input mode |
| 62 | Electronic position fixing system in estimated (dead reckoning) mode |
| 63 | Positioning system inoperative |

([USCG NAVCEN, Class A position report](https://www.navcen.uscg.gov/ais-class-a-reports))

## Corrections

The original MAR-2 specced `mmsiTimestamp(mmsi, embeddedTime)`, described as extracting a timestamp from "MMSI bits 20-40", with a table assigning year, month, day, hour and minute to bits 20 through 47. **This function is fictional and is deleted.**

- An MMSI is a nine-digit identity in the form `MIDXXXXXX`, where the first three digits are the Maritime Identification Digits identifying the country of registry and the remainder is a serial. Other prefixes denote coast stations (`00MIDXXXX`), aids to navigation (`99MIDXXXX`), aircraft (`111MIDXXX`) and similar. **It encodes identity only — there is no timestamp in an MMSI.**
  ([ITU-R M.585](https://www.itu.int/dms_pubrec/itu-r/rec/m/R-REC-M.585-5-200910-S!!PDF-E.pdf))
- The spec was also internally impossible: nine decimal digits is under 30 bits, so bits 20–47 do not exist.

The real problem it was gesturing at — AIS reports carry an under-specified time — is what this story now solves.

## Design notes

- **Reconstruction needs a reference instant.** With only a second-of-minute, the report could belong to any minute. `receivedAt` anchors it, and the correct alignment is the candidate minute boundary nearest the reference, which handles reports received either side of a minute rollover.
- **Reserved values are not seconds.** `quality` is returned alongside the instant so consumers cannot mistake a dead-reckoning marker for a time. For values 60–63 there is no valid second, and `instant` is absent.
- AIS reports UTC. Ship's local time is a separate concern (MAR-18).

## What gmt provides (do not re-implement)

- `toOffsetInstant` from CORE-4 — instant handling
- `floorToZone` from CORE-5 — minute boundary alignment
- `spanMs` from CORE-2 — nearest-boundary selection

## Verification

- `parseAisSecondOfUtc(30, '2024-06-15T12:00:45Z')` aligns to `12:00:30`, not `12:01:30`
- `parseAisSecondOfUtc(58, '2024-06-15T12:01:02Z')` aligns to `12:00:58`, crossing the minute boundary backwards
- Each of 60, 61, 62 and 63 returns the documented quality and no instant
- Values outside 0–63 return the sentinel
- `parseAisBaseStationTime` round-trips a known message 4 field set
- `navTimestamp` emits a `Z` suffix at second precision
- `pnpm run validate` stays green

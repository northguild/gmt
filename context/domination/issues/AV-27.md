# AV-27 — Aviation: Crew flight duty periods

**Scope:** Maximum flight duty period as a caller-supplied table lookup banded on acclimatised local time, plus acclimatisation state and recurring local-window overlap.

## Gap

The original spec reduced crew duty to `crewDutyWindow(start, end, maxHours)`, with a design note saying `maxHours` is passed by the caller because limits differ by regulator and by airline, and that "GMT does not hardcode limits." That dodges the entire problem: **the caller does not know `maxHours` either**, because it is not a constant. It is a table lookup whose inputs are themselves temporal.

Maximum FDP depends on:

- **Report time**, banded by local time of day
- **Number of flight sectors** in the duty period
- **Acclimatisation state** — which timezone the crew member's body clock is on, which is not where they are
- **The window of circadian low**, a local-time window (02:00–05:59 in one scheme) whose intersection with the duty period constrains the limit

Acclimatisation shifts at roughly one timezone per day, so a crew member flown across six zones yesterday is not acclimatised to where they are standing. Every one of those inputs is a time calculation, which is precisely why it belongs in a temporal library.

The vocabulary is the operator's scheme's: an acclimatisation rule (hours in a theatre, a rest length that resets it, a zones-per-day drift), a circadian-low window, a local-night window and early-start, late-finish and night-duty bands. Every one is a local-time window or a count, and every one is the caller's. This story's functions take those windows and counts as parameters and cite no scheme; the docs label examples by their numbers.

## Scope

- `packages/gmt/src/aviation/calculate/acclimatisation.ts`:
  - `acclimatisedZone(history: { arrivedAt: string, zone: string }[], at: string, options: { zonesPerDay: number, acclimatisedAfter: string, resetAfterRest: string }): { zone: string, offsetFromLocal: string, acclimatised: boolean } | null` — Which zone the crew member is acclimatised to: acclimatised after `acclimatisedAfter` in one zone, reset to the current zone by a rest of at least `resetAfterRest`, drifting `zonesPerDay` otherwise. All three are required; none has a default.
- `packages/gmt/src/aviation/calculate/localWindowOverlap.ts`:
  - `localWindowOverlap(duty: Interval, window: LocalWindow, zone: string): { overlap: string, longestRun: string, encroaches: boolean } | null` — Intersection of a duty period with a recurring local window (CORE-55 `LocalWindow`, midnight wrap allowed) in the given zone. `longestRun` is the longest consecutive stretch of the window inside the period, so a caller can test "eight consecutive hours of the night window" against their own number; `encroaches` is whether any of the window falls inside the period. The circadian-low and local-night windows are two calls with two caller-supplied windows.
- `packages/gmt/src/aviation/calculate/flightDutyPeriod.ts`:
  - `maxFlightDutyPeriod(reportAt: string, sectors: number, options: { table: FdpTable, acclimatisedZone: string }): string | null` — Table lookup, banded on report time in the acclimatised zone.
  - `flightDutyStatus(reportAt: string, now: string, sectors: number, options): { elapsed: string, maximum: string, remaining: string, exceeded: boolean } | null`
  - `classifyDuty(duty: Interval, zone: string, bands: { earlyStart: LocalWindow, lateFinish: LocalWindow, night: LocalWindow }): { earlyStart: boolean, lateFinish: boolean, nightDuty: boolean } | null` — Whether the duty starts inside `earlyStart`, finishes inside `lateFinish`, or touches `night`, in the reference zone. The three bands are required and have no default; the operator's scheme supplies them.
- `FdpTable` is `{ bands: { fromLocalTime: string, toLocalTime: string, bySectors: string[] }[] }`, supplied by the caller.

## Design notes

- **The table is data the caller owns.** FDP tables are amended by their publishers and vary by operation type, augmentation and operator. No table ships, on any path; GMT supplies the shape and the lookup.
- **Report time is banded in the acclimatised zone, not the local zone.** This is the distinction the whole story exists for, and getting it wrong produces a limit that is legal on paper and unsafe in fact.
- **Windows are half-open local windows.** A window written 02:00–05:59 is `{ from: '02:00', to: '06:00' }`, consistent with CORE-6. The circadian-low and local-night windows are recurring local windows built on CORE-55's `recurringWindows`, not re-derived here.
- **Cumulative limits are CORE-76's problem.** Rolling and calendar-period sums over a crew duty log are rule objects there, and `oooiTimes` block times are its `flight` entries. They are not "out of scope"; they are next.
- Augmented crew, split duty, standby and extensions are **not** in scope. Document as unimplemented rather than approximating; an under-restrictive approximation of a safety limit is the worst possible failure mode for this library.
- GMT reports the limit and the remaining time. It does not authorise a flight.

## Corrections

`crewDutyWindow(start, end, maxHours)` is replaced. Passing `maxHours` as a caller-supplied scalar is not a neutral design choice — it relocates the hard, temporal part of the problem (report-time banding, sector count, acclimatisation, WOCL encroachment) outside the library, into consumers with no time-math primitives to solve it. That is the part GMT is uniquely able to do.

- The opt-in FDP reference tables and the two fixed windows (a 02:00–05:59 low and a 22:00–08:00 night) were a regulator's numbers; the windows are now a parameter of one overlap function, `localWindowOverlap`, and no table ships on any path.
- `zonesPerDay` and the schedule-type bands defaulted to a regulation, and `classifyDuty` took a `scheduleType` that chose between two regulated band sets; `zonesPerDay`, `acclimatisedAfter`, `resetAfterRest` and the three bands are required, and the schedule type is gone. Regulator names and clause ids leave the spec.

## What gmt provides (do not re-implement)

- `intersectIntervals` / `clampInterval` from CORE-6 — WOCL and local-night overlap
- `resolveLocal` from CORE-4 — local report-time resolution
- `floorToZone` / `bucketRange` from CORE-5 — acclimatisation day counting
- `recurringWindows` from CORE-55 — the WOCL and local-night windows as recurring local intervals
- `flightLeg` / `oooiTimes` from AV-25 — sector timing

## Verification

- Identical report instants in two different acclimatised zones return different maxima
- With `zonesPerDay: 1` and `acclimatisedAfter: 'PT72H'`, a crew member arriving from six zones away is not acclimatised the following day; `acclimatised` is `false`
- After six days in the new zone, `acclimatisedZone` returns that zone
- `localWindowOverlap` for a duty period fully inside a `{ from: '02:00', to: '06:00' }` window returns a four-hour overlap and `encroaches: true`
- A duty period ending at exactly 02:00 against that window returns zero overlap, consistent with half-open intervals
- `localWindowOverlap` for a duty ending at 23:00 against `{ from: '22:00', to: '08:00' }` returns a one-hour overlap; a 21:00–09:00 rest period against the same window returns `longestRun: 'PT10H'`
- `classifyDuty` with bands `{ earlyStart: { from: '05:00', to: '06:00' }, lateFinish: { from: '23:00', to: '02:00' }, night: { from: '02:00', to: '05:00' } }` flags a 05:30 report and not a 06:30 one, a 23:30 finish and not a 22:30 one, and a duty touching 03:00 as night duty; widening `earlyStart` to 07:00 flags the 06:30 report — changing the band changes the answer, asserted
- Sector count changes the maximum for the same report time
- A report time on a DST-transition day bands against the correct local time
- Missing table, bands or `zonesPerDay` returns the sentinel; no function guesses a limit or a window
- `pnpm run validate` stays green

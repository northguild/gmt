# AV-27 — Aviation: Crew flight duty periods

**Scope:** Maximum flight duty period as a regulated table lookup, with acclimatisation and circadian state.

## Gap

The original spec reduced crew duty to `crewDutyWindow(start, end, maxHours)`, with a design note saying `maxHours` is "passed by the caller (FAA vs EASA vs airline-specific). GMT does not hardcode limits." That dodges the entire problem: **the caller does not know `maxHours` either**, because it is not a constant. It is a table lookup whose inputs are themselves temporal.

Maximum FDP depends on:

- **Report time**, banded by local time of day
- **Number of flight sectors** in the duty period
- **Acclimatisation state** — which timezone the crew member's body clock is on, which is not where they are
- **The WOCL**, the window of circadian low, **02:00–05:59 local**, whose intersection with the duty period constrains the limit

Acclimatisation shifts at roughly one timezone per day, so a crew member flown across six zones yesterday is not acclimatised to where they are standing. Every one of those inputs is a time calculation, which is precisely why it belongs in a temporal library.

Sources: [FAR 117 / WOCL](https://far117understanding.com/tag/wocl/), [EASA FTL](https://www.aviatize.com/glossary/easa-ftl), [FAA Part 117 guide](https://far117understanding.com/wp-content/uploads/2016/03/ftdtguidepart117_dec2015.pdf).

## Scope

- `packages/gmt/src/aviation/calculate/acclimatisation.ts`:
  - `acclimatisedZone(history: { arrivedAt: string, zone: string }[], at: string, options?: { zonesPerDay?: number }): { zone: string, offsetFromLocal: string, acclimatised: boolean }` — Which zone the crew member is acclimatised to, defaulting to one zone per day.
- `packages/gmt/src/aviation/calculate/wocl.ts`:
  - `woclOverlap(duty: Interval, acclimatisedZone: string): { overlap: string, encroaches: boolean }` — Intersection of a duty period with the 02:00–05:59 window in the acclimatised zone.
- `packages/gmt/src/aviation/calculate/flightDutyPeriod.ts`:
  - `maxFlightDutyPeriod(reportAt: string, sectors: number, options: { table: FdpTable, acclimatisedZone: string }): string | null` — Table lookup, banded on report time in the acclimatised zone.
  - `flightDutyStatus(reportAt: string, now: string, sectors: number, options): { elapsed: string, maximum: string, remaining: string, exceeded: boolean } | null`
- `FdpTable` is `{ bands: { fromLocalTime: string, toLocalTime: string, bySectors: string[] }[] }`, supplied by the caller. Reference tables for FAA Part 117 Table B and EASA ORO.FTL.205 Table 2 ship behind the opt-in `@northguild/gmt/aviation/data` subpath, with their source and revision recorded.

## Design notes

- **The table is data, not logic.** FDP tables are amended by regulators and vary by operation type, augmentation and jurisdiction. Bundling them on the default import path would make GMT wrong on a regulator's schedule; supplying the shape and an opt-in reference table is the right split.
- **Report time is banded in the acclimatised zone, not the local zone.** This is the distinction the whole story exists for, and getting it wrong produces a limit that is legal on paper and unsafe in fact.
- **WOCL is 02:00–05:59 local**, an inclusive-of-05:59 window that is four hours wide. Expressed as a half-open interval it is `[02:00, 06:00)`, consistent with CORE-6.
- Augmented crew, split duty, standby and cumulative-fatigue limits are **not** in scope. Document as unimplemented rather than approximating; an under-restrictive approximation of a safety limit is the worst possible failure mode for this library.
- GMT reports the limit and the remaining time. It does not authorise a flight.

## Corrections

`crewDutyWindow(start, end, maxHours)` is replaced. Passing `maxHours` as a caller-supplied scalar is not a neutral design choice — it relocates the hard, temporal part of the problem (report-time banding, sector count, acclimatisation, WOCL encroachment) outside the library, into consumers with no time-math primitives to solve it. That is the part GMT is uniquely able to do.

## What gmt provides (do not re-implement)

- `intersectIntervals` / `clampInterval` from CORE-6 — WOCL overlap
- `resolveLocal` from CORE-4 — local report-time resolution
- `floorToZone` / `bucketRange` from CORE-5 — acclimatisation day counting
- `flightLeg` from AV-25 — sector timing

## Verification

- Identical report instants in two different acclimatised zones return different maxima
- A crew member arriving from six zones away is not acclimatised the following day; `acclimatised` is `false`
- After six days in the new zone, `acclimatisedZone` returns that zone
- `woclOverlap` for a duty period fully inside 02:00–05:59 returns a four-hour overlap and `encroaches: true`
- A duty period ending at exactly 02:00 returns zero overlap, consistent with half-open intervals
- Sector count changes the maximum for the same report time
- A report time on a DST-transition day bands against the correct local time
- Missing table returns the sentinel; the function never guesses a limit
- `pnpm run validate` stays green

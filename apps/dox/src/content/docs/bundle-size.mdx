Every import of `@northguild/gmt` carries the `temporal-polyfill` polyfill, {polyfillFigures.floorGzipped} gzipped ({polyfillFigures.floorMinified} minified). That is the polyfill row: no import is smaller than it. GMT's own code is what a row adds above that floor. <code>{polyfillFigures.smallestName}</code> adds {polyfillFigures.smallestCodeMinified} minified, {polyfillFigures.smallestCodeGzipped} gzipped. The two "over the polyfill" columns show that part for every row.

The `@northguild/gmt` row is the whole package, all {formatCount(gmtStats.functions)} public functions, which is the figure a package-size service such as Bundlephobia reports. A single function from a module costs far less than that row.

<BundleSize />

Sizes come from bundling `packages/gmt/src` with esbuild, minified, as ES modules for a neutral platform. 1 kB is 1,000 bytes. The minified size of each row is gated: the repository's check fails when it passes the budget in the last column, and a budget changes only by a reviewed edit. Gzipped sizes are reported and never gated, because they vary with the version of zlib. The comparison below also bundles the last release on `@js-temporal/polyfill`, `@northguild/gmt` {polyfillFigures.previousGmt}, with the same esbuild settings.

## Why GMT uses temporal-polyfill

GMT reads and returns ISO 8601 strings and does its date arithmetic with `Temporal`. Every bundle includes a polyfill for it until a stable Safari ships `Temporal` (see the end of this page). The polyfill is the largest part of almost every import, so its size sets how large GMT is to install.

`temporal-polyfill` {polyfillFigures.shippedVersion} is {polyfillFigures.floorGzipped} gzipped. `@js-temporal/polyfill` {polyfillFigures.previousVersion}, the polyfill of GMT releases up to {polyfillFigures.previousGmt}, is {polyfillFigures.previousFloorGzipped}: a difference of {polyfillFigures.floorDifferenceGzipped} on every import.

## Why there is no build without the polyfill

A build on the `Temporal` built into each runtime would leave out the polyfill and carry only GMT's code, {polyfillFigures.smallestCodeGzipped} to {polyfillFigures.largestCodeGzipped} gzipped for each function measured. GMT does not publish one, because the built-in engines give wrong answers, and different wrong answers from each other.

Every week, GMT runs its whole test suite on the `Temporal` built into Node 26, Chromium, Firefox and WebKit, the engine in Safari. {nativeFailures.total} of GMT's tests get a wrong answer from at least one of them and the right answer from `temporal-polyfill` in the same runtime:

| Built-in `Temporal` | GMT tests it fails |
| --- | --- |
| Node 26 | {nativeFailures.node} |
| Chromium | {nativeFailures.chromium} |
| Firefox | {nativeFailures.firefox} |
| WebKit | {nativeFailures.webkit} |

Each engine fails its own tests, for its own bugs: Node and Chromium share one engine, and Firefox and WebKit each have another. On a build without the polyfill, one call could give a different answer in each browser, and on a runtime that has no `Temporal` it would not run at all. The bugs behind them are listed under [Native engines](/upstream/#native-engines), with the report for each one filed so far.

GMT does not ship code that it knows gives a wrong answer. A bug it finds is fixed before the release that would carry it, never shipped and written up as a known issue ([Zero known bugs](/guides/concepts/correct-at-the-edges/#zero-known-bugs)). A build without the polyfill would ship every one of these failures, so there is none. On `temporal-polyfill`, GMT gives the standard's answer in each case.

The polyfill stays until a stable Safari ships `Temporal` and the weekly run against native `Temporal` passes on Node 26, Chromium, Firefox and WebKit for 12 weeks running ([#316](https://github.com/northguild/gmt/issues/316)).

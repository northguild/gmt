---
title: Zoned Date Operations
description: Common mistakes when working with zoned dates and timezones in GMT.
---

Zoned operations in GMT expose DST disambiguation, calendar annotations, and
timezone offset control that plain operations simply do not have. The mistakes
here cover the ways that extra power bites.

## Mistakes

import Mistake from "../../../components/Mistake.astro";

<Mistake
  severity="high"
  title="Writing the calendar annotation in RFC 9557 order"
  description="GMT's calendar-annotated zoned string puts [u-ca=...] before the time zone — the reverse of RFC 9557 — because its date digits are calendar-native, not ISO. A string in RFC 9557 order looks correct but is rejected by convertZonedToCalendar and the other calendar-aware zoned functions."
  wrongCode={`convertZonedToCalendar("0006-03-15T10:00:00+09:00[Asia/Tokyo][u-ca=japanese;era=reiwa]", "gregorian");
// "" — RFC 9557 order is rejected`}
  rightCode={`import { convertZonedToCalendar } from "@northguild/gmt/zoned";

convertZonedToCalendar("0006-03-15T10:00:00+09:00[u-ca=japanese;era=reiwa][Asia/Tokyo]", "gregorian");
// "2024-03-15T10:00:00+09:00[Asia/Tokyo]" — calendar annotation first`}
/>

<Mistake
  severity="high"
  title="Passing a calendar-annotated value to convertPlainDateTimeToZoned"
  description="convertPlainDateTimeToZoned has no calendar grammar: a [u-ca=...] annotation makes the input invalid, and the result is an empty string. Convert the Gregorian wall time first, then express the zoned result in the calendar with convertZonedToCalendar."
  wrongCode={`convertPlainDateTimeToZoned("2024-03-15T00:00:00[u-ca=japanese]", "Asia/Tokyo");
// "" — the annotation is invalid input here`}
  rightCode={`import { convertPlainDateTimeToZoned, convertZonedToCalendar } from "@northguild/gmt/zoned";

const z = convertPlainDateTimeToZoned("2024-03-15T00:00:00", "Asia/Tokyo");
// "2024-03-15T00:00:00.000+09:00[Asia/Tokyo]"
convertZonedToCalendar(z, "japanese");
// "0006-03-15T00:00:00+09:00[u-ca=japanese;era=reiwa][Asia/Tokyo]"`}
/>

<Mistake
  severity="high"
  title="Assuming every zoned/ function accepts the annotation"
  description="Only the calendar-aware subset — addZoned, subtractZoned, diffZoned, diffZonedAsDuration, convertZonedToCalendar and the zoned interval functions — accepts GMT's calendar-annotated zoned string, and there calendar units resolve in that calendar. Every other zoned/ function treats the annotation as invalid input."
  wrongCode={`startOfZoned("0006-03-15T10:00:00+09:00[u-ca=japanese;era=reiwa][Asia/Tokyo]", "day");
// "" — startOfZoned does not accept the annotation`}
  rightCode={`import { addZoned } from "@northguild/gmt/zoned";

addZoned("0006-01-31T00:00:00+09:00[u-ca=japanese;era=reiwa][Asia/Tokyo]", { months: 1 });
// "0006-02-29T00:00:00+09:00[u-ca=japanese;era=reiwa][Asia/Tokyo]" — month arithmetic in the Japanese calendar`}
/>

<Mistake
  severity="high"
  title="Using offset instead of IANA timezone"
  description="An offset like '-05:00' is not a time zone: it has no DST rules, so it could never become EDT. GMT's zoned functions reject it and return their sentinel. The IANA zone identifier, such as 'America/New_York', is the only correct argument."
  wrongCode={`getZonedNow("-05:00"); // "" — an offset is not an IANA zone`}
  rightCode={`import { getZonedNow } from "@northguild/gmt/zoned";

getZonedNow("America/New_York"); // switches between EST and EDT automatically`}
/>

<Mistake
  severity="high"
  title="Not validating timezone before use"
  description="An invalid timezone string silently produces the invalid-input sentinel from every zoned function — an empty string, or null from those that return a number. Always run isValidTimeZone first."
  wrongCode={`getZonedNow("not-a-zone"); // ""`}
  rightCode={`import { isValidTimeZone, getZonedNow } from "@northguild/gmt/zoned";

if (isValidTimeZone("America/New_York")) {
getZonedNow("America/New_York"); // safe
}`}
/>

<Mistake
  severity="high"
  title="Assuming addZoned/subtractZoned rejects DST gaps"
  description="addZoned and subtractZoned never reject a spring-forward gap. Temporal's arithmetic moves a result that lands in a gap past it before disambiguation is consulted, so even disambiguation: 'reject' returns the moved time. The option acts only on a result that lands in a fall-back overlap."
  wrongCode={`addZoned("2024-03-09T02:30:00-05:00[America/New_York]", { days: 1 }, { disambiguation: "reject" });
// "2024-03-10T03:30:00-04:00[America/New_York]" — the gap landing is not rejected`}
  rightCode={`// disambiguation decides a fall-back overlap landing
addZoned("2024-11-02T01:30:00-04:00[America/New_York]", { days: 1 }, { disambiguation: "reject" });
// ""
addZoned("2024-11-02T01:30:00-04:00[America/New_York]", { days: 1 }, { disambiguation: "later" });
// "2024-11-03T01:30:00-05:00[America/New_York]"`}
/>

<Mistake
  severity="high"
  title="Passing offset: 'prefer' with disambiguation"
  description="The `offset` option ('prefer', 'use', 'ignore', 'reject') decides whether the input's own UTC offset is kept, and the `disambiguation` option ('compatible', 'earlier', 'later', 'reject') resolves a wall time the offset does not settle. With 'prefer', an offset that is still valid settles the time, so disambiguation never runs."
  wrongCode={`setZoned("2024-11-03T01:45:00-05:00[America/New_York]", { minute: 0 }, {
  offset: "prefer",
  disambiguation: "reject"
}); // "2024-11-03T01:00:00-05:00[America/New_York]" — -05:00 kept, reject never fired`}
  rightCode={`setZoned("2024-11-03T01:45:00-05:00[America/New_York]", { minute: 0 }, {
  disambiguation: "reject"
}); // "" — offset defaults to 'ignore', so reject fires on the overlap`}
/>

<Mistake
  severity="high"
  title="Expecting disambiguation: 'reject' to throw"
  description="GMT functions never throw: a rejected wall time returns an empty string. With setZoned's default offset: 'ignore', disambiguation: 'reject' fires on a spring-forward gap and on a fall-back overlap alike. Check the result instead of wrapping the call in try/catch."
  wrongCode={`try {
  setZoned("2024-03-09T02:30:00-05:00[America/New_York]", { day: 10 }, { disambiguation: "reject" });
} catch {
  // never reached — 02:30 on 10 March is in the gap, and the result is ""
}`}
  rightCode={`const r = setZoned("2024-03-09T02:30:00-05:00[America/New_York]", { day: 10 }, { disambiguation: "reject" }); // ""
if (r === "") {
  // invalid input, or a wall time in a gap or an overlap
}`}
/>

<Mistake
  severity="medium"
  title="Confusing hasDaylightSaving, getDstTransitions, and isInDaylightSaving"
  description="hasDaylightSaving tells you whether a zone *ever* has DST. getDstTransitions returns the transitions in one year. isInDaylightSaving tells you whether a specific instant is in DST. They answer three different questions."
  wrongCode={`hasDaylightSaving("America/New_York"); // true — the zone has DST
// used to check whether a specific date is in DST — wrong function`}
  rightCode={`import { isInDaylightSaving, getDstTransitions } from "@northguild/gmt/zoned";

isInDaylightSaving("2024-07-01T12:00:00-04:00[America/New_York]"); // true
getDstTransitions("America/New_York", 2024);
// [
//   { instant: "2024-03-10T07:00:00Z", offsetBefore: "-05:00", offsetAfter: "-04:00" },
//   { instant: "2024-11-03T06:00:00Z", offsetBefore: "-04:00", offsetAfter: "-05:00" },
// ]`}
/>

<Mistake
  severity="medium"
  title="Reaching for cycleZoned when calendar arithmetic is wanted (or vice versa)"
  description="cycleZoned moves one field around its own range and wraps without carrying into the next field. addZoned/subtractZoned with calendar units carry across month and year boundaries. They are not interchangeable."
  wrongCode={`cycleZoned("2024-12-15T00:00:00-05:00[America/New_York]", "month", 1);
// "2024-01-15T00:00:00-05:00[America/New_York]" — wraps within the year`}
  rightCode={`import { addZoned } from "@northguild/gmt/zoned";

addZoned("2024-12-15T00:00:00-05:00[America/New_York]", { months: 1 });
// "2025-01-15T00:00:00-05:00[America/New_York]" — calendar arithmetic`}
/>

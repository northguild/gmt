A GTFS feed is a set of CSV files that describe a transit service. Its times are not clock
readings. A trip that leaves at 23:40 and reaches its last stop after midnight does not restart
the count at `00:00:00`. The stop is written `25:35:00` and stays part of the service day the trip
began on.

The functions here read that form, write it back and check it. They keep the whole days past the
service day and the seconds left over as two numbers, and they never name a date.

```typescript
import { parseGtfsTime } from "@northguild/gmt/rail/parse";
import { formatGtfsTime } from "@northguild/gmt/rail/format";
import { isValidGtfsTime } from "@northguild/gmt/rail/validate";
```

The functions live in `@northguild/gmt/rail/parse`, `@northguild/gmt/rail/format` and
`@northguild/gmt/rail/validate`.

## The GTFS time form

The GTFS Schedule Reference defines the `Time` type as "Time in the HH:MM:SS format (H:MM:SS is
also accepted)". Minutes and seconds are two digits. The type is used by
`arrival_time`, `departure_time`, `start_pickup_drop_off_window` and `end_pickup_drop_off_window`
in `stop_times.txt`, by `start_time` and `end_time` in `frequencies.txt`, and by
`prior_notice_last_time` and `prior_notice_start_time` in `booking_rules.txt`.

GTFS states no upper bound for the hours, so the bound is GMT's. MobilityData's gtfs-validator
reads one, two or three hour digits, and GMT does the same, so the hours run from 0 to 999. The minutes and the seconds run from 00 to 59, and the digits are ASCII digits.

## Times past midnight

For a time after midnight on the service day, the reference says to "enter the time as a value
greater than 24:00:00", and gives `25:35:00` as "1:35AM on the next day". Its definition of a
service day says one "may exceed 24:00:00", and gives a day that runs from `08:00:00` to
`26:00:00`.

Its example of blocks and service days has a `trip_3` that runs from `24:00:00` to `24:55:00`.
The reference says it is part of the Friday service day. So `24:00:00` is the midnight at the end
of the service day, and it is not the start of the next one.

## Reading

[`parseGtfsTime(value)`](/reference/rail/parse/parseGtfsTime/) returns a record with two numbers.
`seconds` is the written time less whole 24-hour blocks, from 0 to 86399, and it is not always the
clock time (see below). `dayOverflow` is the number of whole days past the service day: 0 before
`24:00:00`, 1 from `24:00:00`, and so on. It returns `null` for anything that is not a GTFS time.

```typescript
import { parseGtfsTime } from "@northguild/gmt/rail/parse";

parseGtfsTime("25:35:00");
// { seconds: 5700, dayOverflow: 1 }
parseGtfsTime("8:05:00");
// { seconds: 29100, dayOverflow: 0 }
parseGtfsTime("24:00:00");
// { seconds: 0, dayOverflow: 1 }
parseGtfsTime("48:00:00");
// { seconds: 0, dayOverflow: 2 }
parseGtfsTime("1000:00:00");
// null (three hour digits at most)
```

## Why the overflow is kept apart

The record holds the days past the service day apart from the time of day because folding them
together loses one. Code that takes the hours modulo 24 turns `25:35:00` into `01:35:00`, and
`01:35:00` is a time at the start of a service day. The stop that belonged at the end of the
night now sorts before the stops that came before it.

The library keeps both numbers, and writes them back as the same text.

```typescript
import { parseGtfsTime } from "@northguild/gmt/rail/parse";
import { formatGtfsTime } from "@northguild/gmt/rail/format";

const record = parseGtfsTime("25:35:00");
// { seconds: 5700, dayOverflow: 1 }

if (record !== null) {
  formatGtfsTime(record);
  // "25:35:00"
}
```

## Writing a time back

[`formatGtfsTime(record)`](/reference/rail/format/formatGtfsTime/) writes the form back with at
least two hour digits, so `8:05:00` is written `08:05:00`. It writes three hour digits when it has
to: VIA Rail's feed, for one, has a stop at `110:29:00`. A record it
cannot write gives `""`: seconds outside 0 to 86399, a negative or fractional count of days,
or hours above 999.

```typescript
import { formatGtfsTime } from "@northguild/gmt/rail/format";

formatGtfsTime({ seconds: 29100, dayOverflow: 0 });
// "08:05:00" (read from 8:05:00)
formatGtfsTime({ seconds: 52140, dayOverflow: 4 });
// "110:29:00"
formatGtfsTime({ seconds: 5700, dayOverflow: 0 });
// "01:35:00"
formatGtfsTime({ seconds: 5700, dayOverflow: 42 });
// "" (1009 hours)
formatGtfsTime({ seconds: 86400, dayOverflow: 0 });
// "" (a whole day belongs in dayOverflow)
```

## Checking a value

[`isValidGtfsTime(value)`](/reference/rail/validate/isValidGtfsTime/) reads the value the same way
the parser does, so it is true exactly when the parser returns a record.

```typescript
import { isValidGtfsTime } from "@northguild/gmt/rail/validate";

isValidGtfsTime("25:35:00");
// true
isValidGtfsTime("25:60:00");
// false (minute 60)
isValidGtfsTime("1000:00:00");
// false
isValidGtfsTime("25:35");
// false (no seconds)
isValidGtfsTime(" 25:35:00");
// false (a leading space)
isValidGtfsTime("");
// false
```

Nothing is trimmed. The reference asks that "extra spaces between fields or field names should be
removed" because "many parsers consider the spaces to be part of the value", and says a value
must not hold tabs, carriage returns or new lines. It also says files with a byte-order mark are
acceptable. Taking out the spaces and the mark is the job of the CSV reader that splits the row,
so a stray space reaches these functions as a refusal, not as a quiet repair.

A check made for clock times does not do this job. `isValidTime("25:35:00")` from
`@northguild/gmt/plain/validate` is `false`, because there is no 25th hour on a clock.

## Not a clock reading yet

The reference measures the time "from 'noon minus 12h' of the service day (effectively midnight
except for days on which daylight savings time changes occur)". So `dayOverflow × 86400 + seconds`
is the elapsed time from that point, and it matches the wall clock only when no clock change falls
between that point and the time.

```typescript
import { parseGtfsTime } from "@northguild/gmt/rail/parse";

const record = parseGtfsTime("25:35:00");

if (record !== null) {
  record.dayOverflow * 86400 + record.seconds;
  // 92100 (seconds from noon minus 12 h of the service day)
}
```

A clock change on the night after the service day is enough to break the match. In Berlin the
clocks go forward from 02:00 to 03:00 early on Sunday 29 March 2026. For the service day Saturday
28 March, `26:30:00` is 26 hours 30 minutes after Saturday 00:00, which is 03:30 on Sunday, not the
02:30 that reading it as a clock gives.

Turning a record into an instant needs the agency's time zone and the service date. That is what
`gtfsToInstant`, planned for a later release, will do. Until then the record is what you keep.

## What this layer does not do

- It does not pick the service days a trip runs on. That is `calendar.txt` and
  `calendar_dates.txt`.
- It does not read the GTFS `Date` type or the `Local time` type.
- It does not split a CSV row. It reads one field.

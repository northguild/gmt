Airlines and airports exchange schedules in the files and messages of IATA's Standard Schedules
Information Manual, SSIM. Their dates are not ISO 8601. An SSIM date is written `01JAN26`: two
digits of day, three letters of month and two digits of year. Nothing in it says which century
the year is in, and the month is a code, not a word in any language.

Weather reports and notices to air missions have the same problem. A METAR writes its time as
`251200Z`: day, hour and minute, and no month. A NOTAM writes its validity as ten digits,
`1407031230`, with a two-digit year, and sometimes adds `EST` or writes `PERM` in place of a time.

The functions here read and write these values and check them. They never read the platform's
language, they never choose a century for you, and they never read the clock to find a month.

```typescript
import { parseSsimDate } from "@northguild/gmt/aviation/parse";
import { formatSsimDate } from "@northguild/gmt/aviation/format";
import { isValidSsimDate } from "@northguild/gmt/aviation/validate";
import { parseMetarTime, parseNotamValidity } from "@northguild/gmt/aviation/parse";
import { isValidMetarTime, isValidNotamValidity } from "@northguild/gmt/aviation/validate";
```

The functions live in `@northguild/gmt/aviation/parse`, `@northguild/gmt/aviation/format` and
`@northguild/gmt/aviation/validate`. They use only Core: a date check from
[`plain/`](/reference/plain/) and the library's two-digit-year window.

## The SSIM date form

The form is day, month letters, year: `01JAN26`. EUROCONTROL's CSST guide shows it in a schedule
file, in the carrier record, the second record of the file. Its period of schedule validity
runs from `05APR10` to `11APR10`, and a third date, `16DEC09`, follows (the figure does not
label it). The three are written together as `05APR1011APR1016DEC09`. The month letters are the
first three letters of the English month name in upper case: `JAN`, `FEB`, `MAR`, `APR`, `MAY`,
`JUN`, `JUL`, `AUG`, `SEP`, `OCT`, `NOV`, `DEC`.

[`parseSsimDate(value, options)`](/reference/aviation/parse/parseSsimDate/) returns an ISO date.
It returns `""` for anything that is not a valid SSIM date.

```typescript
import { parseSsimDate } from "@northguild/gmt/aviation/parse";

parseSsimDate("01JAN26", { yearWindow: 2000 });
// "2026-01-01"
parseSsimDate("05APR10", { yearWindow: 2000 });
// "2010-04-05"
parseSsimDate("16DEC09", { yearWindow: 1950 });
// "2009-12-16"
parseSsimDate("29FEB25", { yearWindow: 2000 });
// "" (no 29 February in 2025)
parseSsimDate("31APR26", { yearWindow: 2000 });
// "" (no 31 April)
parseSsimDate("00XXX00", { yearWindow: 2000 });
// "" (XXX is not a month)
```

Slot messages write the day and month with no year (`01APR`), as ACL's introductory guide shows.
This layer does not read that form, because a date with no year needs a season to anchor it.

## Why the month letters bypass the locale

The letters are a code. `JAN` is the code for January in every file, whatever language the
machine reading it uses. A pattern parser that is given the platform's language breaks on this
in both directions. On a machine set to Spanish it rejects `JAN` and accepts `ENE`, which the
format never writes. Other languages want their own words, such as `JANV.` with its full stop.
And it accepts lower case, `jan`, which the format never writes either.

`parseSsimDate` reads the letters from a constant table. The platform's language is never read,
so the answer is the same on every machine.

```typescript
import { parseSsimDate } from "@northguild/gmt/aviation/parse";

parseSsimDate("01JAN26", { yearWindow: 2000 });
// "2026-01-01" (on every machine)
parseSsimDate("01ENE26", { yearWindow: 2000 });
// "" (Spanish for January; not an SSIM month)
parseSsimDate("01JANV26", { yearWindow: 2000 });
// "" (letters from another language)
parseSsimDate("01jan26", { yearWindow: 2000 });
// "" (lower case)
parseSsimDate("01Jan26", { yearWindow: 2000 });
// "" (mixed case)
```

Upper case only is deliberate. A reader that accepts `jan` invites a writer that emits it, and
folding case can change a letter: `"ſEP".toUpperCase() === "SEP"` maps another letter onto a
month code, and `"i".toLocaleUpperCase("tr") === "İ"` depends on the locale.

## The window

A two-digit year does not say which century it is in. `parseSsimDate` takes the hundred-year
window you state in `yearWindow`, and returns `""` without one. There are two ways to state it.

A fixed first year suits an archive, because the same file then reads the same way in any year.
`yearWindow: 2000` places `YY` in 2000 to 2099, and `yearWindow: 1950` places it in 1950 to
2049.

```typescript
import { parseSsimDate } from "@northguild/gmt/aviation/parse";

parseSsimDate("01JAN26", { yearWindow: 2000 });
// "2026-01-01"
parseSsimDate("01JAN26", { yearWindow: 1900 });
// "1926-01-01"
parseSsimDate("01JAN70", { yearWindow: 1970 });
// "1970-01-01"
parseSsimDate("01JAN70", { yearWindow: 1971 });
// "2070-01-01"
```

`"rolling"` suits a live feed. The window moves with the current UTC year, so a date near today
is read as near today.

```typescript
import { parseSsimDate } from "@northguild/gmt/aviation/parse";

parseSsimDate("01JAN26", { yearWindow: "rolling" });
// "2026-01-01" (while the current UTC year is 1977 to 2076)
parseSsimDate("01JAN26", {});
// "" (no window stated)
```

The window also settles whether a day exists. `29FEB00` is a date from 2000, which was a leap
year, and nothing from 1900, which was not:

```typescript
import { parseSsimDate } from "@northguild/gmt/aviation/parse";

parseSsimDate("29FEB00", { yearWindow: 2000 });
// "2000-02-29"
parseSsimDate("29FEB00", { yearWindow: 1900 });
// ""
```

The library holds no cut-off year of its own. Any fixed pivot is right for the files of one
period and wrong for the others, and it would change its answer on the day it was passed. The
century is a fact about your files, so you state it.

## Writing a date back

[`formatSsimDate(value, options)`](/reference/aviation/format/formatSsimDate/) writes an ISO date
as an SSIM date, with upper-case letters. It takes the same window, and it returns `""` for a
year outside it, because the two digits it would write would read back as another year.

```typescript
import { formatSsimDate } from "@northguild/gmt/aviation/format";

formatSsimDate("2026-01-01", { yearWindow: 2000 });
// "01JAN26"
formatSsimDate("2000-02-29", { yearWindow: 2000 });
// "29FEB00"
formatSsimDate("2026-01-01", { yearWindow: 1900 });
// "" (2026 is outside 1900 to 1999)
formatSsimDate("2100-01-01", { yearWindow: 2000 });
// "" (2100 is outside 2000 to 2099)
formatSsimDate("2026-01-01", {});
// "" (no window stated)
```

A round trip never changes a century. Whatever the formatter writes, the parser reads back to the
same date in the same window:

```typescript
import { formatSsimDate } from "@northguild/gmt/aviation/format";
import { parseSsimDate } from "@northguild/gmt/aviation/parse";

formatSsimDate("1999-12-31", { yearWindow: 1950 });
// "31DEC99"
parseSsimDate("31DEC99", { yearWindow: 1950 });
// "1999-12-31"
```

## The METAR report time

A METAR opens with a group of six digits and a letter: `YYGGggZ`. `YY` is the day of the month,
`GG` the hour, `gg` the minute, and `Z` says the time is UTC. WMO-No. 306 gives the group for a
METAR and a SPECI (FM 15, regulation 15.3.1) and for the issue time of a TAF (FM 51,
regulation 51.1.2). The `Z` follows the digits with no space.

[`parseMetarTime(value, referenceInstant)`](/reference/aviation/parse/parseMetarTime/) returns an
ISO instant in UTC. It returns `""` for anything that is not a METAR time group, and for a
reference that is not an instant with `Z` or an offset.

```typescript
import { parseMetarTime } from "@northguild/gmt/aviation/parse";

parseMetarTime("251200Z", "2024-06-25T12:20:00Z");
// "2024-06-25T12:00:00Z"
parseMetarTime("251200", "2024-06-25T12:20:00Z");
// "" (no Z)
parseMetarTime("251200z", "2024-06-25T12:20:00Z");
// "" (lower case)
parseMetarTime("252400Z", "2024-06-25T12:20:00Z");
// "" (hour 24)
parseMetarTime("251200Z", "2024-06-25T12:20:00");
// "" (the reference has no offset)
```

## Choosing the month

The group names no month and no year, so the function needs a reference: the time the report
was received, or the timestamp the archive stored with it. It is required. The function never
uses the current time, because an archive read in March must give the same answer as one read
in October.

The result is the candidate nearest the reference in exact time. The candidates are the latest
one at or before the reference and the earliest one after it. A report is usually a few minutes
old, so a group just before the end of a month, read just after the start of the next, belongs to
the month before:

```typescript
import { parseMetarTime } from "@northguild/gmt/aviation/parse";

parseMetarTime("302350Z", "2024-07-01T00:05:00Z");
// "2024-06-30T23:50:00Z" (30 days ahead if you assume the current month)
parseMetarTime("010010Z", "2024-06-30T23:55:00Z");
// "2024-07-01T00:10:00Z" (a clock that runs ahead of the sender)
parseMetarTime("312350Z", "2025-01-01T00:05:00Z");
// "2024-12-31T23:50:00Z" (back across a year)
```

A month that lacks the day is skipped. June has no 31st, so `312350Z` received just after
midnight on 1 July is from 31 May, which is nearer than 31 July. February has no 31st either:
two months back is the nearest 31st.

```typescript
import { parseMetarTime } from "@northguild/gmt/aviation/parse";

parseMetarTime("312350Z", "2024-07-01T00:05:00Z");
// "2024-05-31T23:50:00Z"
parseMetarTime("312359Z", "2024-03-01T00:00:00Z");
// "2024-01-31T23:59:00Z"
```

When two candidates are equally near, the earlier wins. This is GMT's rule, not WMO's. A group of `151200Z` read at noon on 30 June is exactly 15 days from each
neighbour. One nanosecond later, the later one is nearer:

```typescript
import { parseMetarTime } from "@northguild/gmt/aviation/parse";

parseMetarTime("151200Z", "2024-06-30T12:00:00Z");
// "2024-06-15T12:00:00Z" (a tie: the earlier)
parseMetarTime("151200Z", "2024-06-30T12:00:00.000000001Z");
// "2024-07-15T12:00:00Z"
```

The months are counted in UTC, whatever offset the reference carries. A reference of
`2024-07-01T00:05:00+02:00` is 22:05 UTC on 30 June:

```typescript
import { parseMetarTime } from "@northguild/gmt/aviation/parse";

parseMetarTime("302350Z", "2024-07-01T00:05:00+02:00");
// "2024-06-30T23:50:00Z"
parseMetarTime("302350Z", "2024-06-30T20:05:00-04:00");
// "2024-06-30T23:50:00Z"
```

The function sets no limit on how far the result may be from the reference. If your reference
is a year after the report, you get a time in the wrong year. Check staleness with
[`spanNs`](/reference/span/calculate/spanNs/) before you trust the answer.

## NOTAM validity

A NOTAM states when it starts in item B) and when it ends in item C). Each is ten digits,
`YYMMDDHHMM`, in UTC. ICAO's NOTAM format (PANS-AIM, Appendix 3) also lets item C) end in `EST`,
to say the end is an estimate, or be the word `PERM`, to say there is no end. EUROCONTROL's OPADD,
which applies the format across Europe, adds that there is no space before `EST`.

[`parseNotamValidity(value, options)`](/reference/aviation/parse/parseNotamValidity/) returns one
of two objects, or `null` for anything it does not read. It reads one group at a time, with no
`B)` or `C)` label.

```typescript
import { parseNotamValidity } from "@northguild/gmt/aviation/parse";

parseNotamValidity("2506151200", { yearWindow: 2000 });
// { kind: "instant", instant: "2025-06-15T12:00:00Z", estimated: false }
parseNotamValidity("1407031230EST", { yearWindow: 2000 });
// { kind: "instant", instant: "2014-07-03T12:30:00Z", estimated: true }
parseNotamValidity("PERM", { yearWindow: 2000 });
// { kind: "permanent" }
parseNotamValidity("1407031230 EST", { yearWindow: 2000 });
// null (OPADD writes no space before EST)
```

`PERM` is a state, not a date. A permanent NOTAM has no end, so the function returns
`{ kind: "permanent" }` and not a far-future instant. If you turn `PERM` into `9999-12-31`, a
check that asks "is it in force?" is right until that day and wrong after it. With a state, there
is nothing to compare, and your code has to say what permanent means.

`EST` keeps its instant. The time is the estimate the originator gave, and the NOTAM may be
replaced or cancelled before it. The result carries `estimated: true`, so you can show it as an
estimate. Dropping the flag turns a guess into a promise.

The function does not know which item it is reading. In item B) both `EST` and `PERM` are
malformed, so check `kind` and `estimated` yourself when you read a start time.

The century is the caller's, as for SSIM, and it also applies to `PERM`: without `yearWindow` the
result is `null` for every value. `"rolling"` suits a live feed.

```typescript
import { parseNotamValidity } from "@northguild/gmt/aviation/parse";

parseNotamValidity("9912312359EST", { yearWindow: 1950 });
// { kind: "instant", instant: "1999-12-31T23:59:00Z", estimated: true }
parseNotamValidity("5001010000", { yearWindow: 1950 });
// { kind: "instant", instant: "1950-01-01T00:00:00Z", estimated: false }
parseNotamValidity("2506151200", {});
// null (no window stated)
```

Nothing is corrected. ICAO ends a day at `2359` and says not to write `2400`, and OPADD does not
allow `WIE`, `UFN` or `APRX DUR`. A reader that rounds them into something valid hides a message
that broke the rules, so each of these returns `null`, as does a month, day, hour or minute that
does not exist:

```typescript
import { parseNotamValidity } from "@northguild/gmt/aviation/parse";

parseNotamValidity("2506152400", { yearWindow: 2000 });
// null (do not use 2400)
parseNotamValidity("WIE", { yearWindow: 2000 });
// null
parseNotamValidity("UFN", { yearWindow: 2000 });
// null
parseNotamValidity("2502291200", { yearWindow: 2000 });
// null (2025 has no 29 February)
parseNotamValidity("0002290000", { yearWindow: 2000 });
// { kind: "instant", instant: "2000-02-29T00:00:00Z", estimated: false }
```

## Checking a value

[`isValidSsimDate(value, options)`](/reference/aviation/validate/isValidSsimDate/) takes the same
window and answers with a boolean. It is `true` exactly when `parseSsimDate` returns a date.

```typescript
import { isValidSsimDate } from "@northguild/gmt/aviation/validate";

isValidSsimDate("01JAN26", { yearWindow: 2000 });
// true
isValidSsimDate("29FEB00", { yearWindow: 2000 });
// true
isValidSsimDate("29FEB00", { yearWindow: 1900 });
// false
isValidSsimDate("01jan26", { yearWindow: 2000 });
// false
isValidSsimDate("01JAN26", {});
// false
```

The window is part of the question. `29FEB00` is neither valid nor invalid until you say which
century it is in.

[`isValidMetarTime(value, referenceInstant)`](/reference/aviation/validate/isValidMetarTime/) and
[`isValidNotamValidity(value, options)`](/reference/aviation/validate/isValidNotamValidity/) call
their parsers, so each is `true` exactly when the parser gives a result.

```typescript
import {
  isValidMetarTime,
  isValidNotamValidity,
} from "@northguild/gmt/aviation/validate";

isValidMetarTime("302350Z", "2024-07-01T00:05:00Z");
// true
isValidMetarTime("251200", "2024-06-25T12:20:00Z");
// false
isValidMetarTime("251200Z", "2024-06-25T12:20:00");
// false (the reference has no offset)
isValidNotamValidity("1407031230EST", { yearWindow: 2000 });
// true
isValidNotamValidity("PERM", { yearWindow: 2000 });
// true
isValidNotamValidity("PERM", {});
// false
isValidNotamValidity("2506152400", { yearWindow: 2000 });
// false
```

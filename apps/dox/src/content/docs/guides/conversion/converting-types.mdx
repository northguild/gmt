Use these functions when you need to move between representations: a plain datetime
to a zoned one, a UTC string to a Unix epoch, a date in a non-Gregorian calendar.

## Plain to zoned (and back)

```typescript
import { convertPlainDateTimeToZoned, convertZonedToPlainDateTime } from "@northguild/gmt/zoned";

convertPlainDateTimeToZoned("2024-03-15T14:30:45", "America/New_York");
// "2024-03-15T14:30:45.000-04:00[America/New_York]"

convertZonedToPlainDateTime("2024-03-15T14:30:45[America/New_York]");
// "2024-03-15T14:30:45"
```

The plain-to-zoned direction accepts `disambiguation` for DST gap/overlap control —
see [Zoned Operations](/guides/zoned-date-operations/zoned-operations/).

## UTC and Unix

```typescript
import { convertUtcToUnix } from "@northguild/gmt/utc";
import { convertUnixToUtc } from "@northguild/gmt/unix";

convertUtcToUnix("2024-03-15T14:30:45Z"); // 1710513045000 — milliseconds
convertUnixToUtc(1710513045000); // "2024-03-15T14:30:45Z"

// Seconds: pass the unit explicitly, in both directions
convertUtcToUnix("2024-03-15T14:30:45Z", { epochUnit: "seconds" }); // 1710513045
convertUnixToUtc(1710513045, { epochUnit: "seconds" }); // "2024-03-15T14:30:45Z"
```

Both directions default to **milliseconds** and take an optional `{ epochUnit: "seconds" }` — there
are no separate `…Ms` functions. Name the unit whenever you store or send a value, and be
consistent: mixing the two is a common source of 1000x errors.

## Zoned to UTC and back

```typescript
import { convertZonedToUtc } from "@northguild/gmt/zoned";
import { convertUtcToZoned } from "@northguild/gmt/utc";

convertZonedToUtc("2024-03-15T14:30:45[America/New_York]"); // "2024-03-15T18:30:45Z"
convertUtcToZoned("2024-03-15T14:30:45Z", "America/New_York"); // "2024-03-15T10:30:45-04:00[America/New_York]"
```

## Between timezones

```typescript
import { convertZonedToZoned } from "@northguild/gmt/zoned";

convertZonedToZoned("2024-03-15T14:30:45[America/New_York]", "Europe/London");
// "2024-03-15T18:30:45+00:00[Europe/London]"
```

## Non-Gregorian calendar systems

```typescript
import { convertDateToCalendar } from "@northguild/gmt/plain";

convertDateToCalendar("2024-10-03", "hebrew");
// "2024-10-03[u-ca=hebrew]"

convertDateToCalendar("2024-10-03", "japanese");
// "2024-10-03[u-ca=japanese]"
```

The string is the RFC 9557 form `Temporal.PlainDate.prototype.toString()` writes: the ISO
digits, then a `[u-ca=<id>]` annotation naming the calendar. Calendar fields such as the
Hebrew year or the Japanese era are read values, never string content. Convert with
`convertDateToCalendar(value, "iso8601")` to get back to a bare ISO string.

For zoned values, use `convertZonedToCalendar` (zoned namespace) — it keeps the
instant, offset, and IANA zone unchanged. See [Calendar Systems](/guides/core-date-operations/calendar-systems/)
for the full calendar-aware arithmetic story.

`@northguild/gmt` is not the latest entry in a crowded field — it is a
fundamentally different bet about what a date/time library should guarantee.
The pages below make that concrete with data drawn from the library itself.

## CI test execution volume

The most direct measure of testing rigor is how many times the library is
actually executed in CI. GMT's suite is {formatCount(gmtStats.tests)} tests, and its {gmtStats.locales}-locale
matrix is built into those tests rather than layered on top. On every PR, CI
then re-runs the whole suite under {gmtStats.timezones} timezones and {gmtStats.nodes.length} Node
versions, so every test runs {runsPerTest} times.

## Timezone coverage

GMT tests against {gmtStats.timezones} timezones chosen not for geographic spread but for offset coverage — from {formatOffset(zoneOffsets.min.minutes)} ({zoneOffsets.min.zoneId}) to {formatOffset(zoneOffsets.max.minutes)} ({zoneOffsets.max.zoneId}). That {offsetWindowHours}-hour window means that at any given moment, at least one zone is already living in tomorrow while another is still stuck in yesterday. Date-boundary bugs — off-by-one day, wrong month rollover, DST gaps — only surface when the suite runs across this full offset range. A test that passes at UTC can fail at UTC+14 simply because the calendar date is different.

## Locale matrix

GMT does not test every locale — there are hundreds, and most differ only in formatting minutiae. Instead it tests a curated matrix of {gmtStats.locales} locales chosen to stress the dimensions that actually break date libraries: script direction (LTR/RTL Arabic and Hebrew), character sets (CJK, Cyrillic, Latin), pluralization rules, and ICU data variants. The goal is not exhaustive locale coverage — it is representative coverage of every class of bug that locale-aware code can produce.

## Correct at the edges

Most date bugs hide at the extremes, where ordinary tests never look. GMT tests them directly:

<div class="gmt-checklist">

- **Midnight.** A time at the last nanosecond of the day stays on that day.
- **The ends of time.** The first and last moments a date can represent still give exact answers.
- **Daylight saving.** Days, weeks and months start at the right moment across clock changes, right to the end of the calendar.
- **Zones ahead of UTC.** Sydney and Kiritimati work right up to the last moment that can be represented.
- **Long totals.** Adding up time stays exact to the nanosecond, however large the total.
- **Touching intervals.** A 9–5 meeting and a 5–6 meeting don't overlap: an interval includes its start, not its end.
- **Zero known bugs.** None of the {formatCount(gmtStats.tests)} tests is skipped or switched off.

</div>

[See the evidence behind each of these →](/guides/concepts/correct-at-the-edges/) · Where the Temporal polyfill gets one of these wrong, GMT returns the spec's answer and reports the defect upstream: [Helping fix Temporal →](/upstream/)

## What this means

| Dimension             | GMT                                              | Legacy libraries                                                    |
| --------------------- | ------------------------------------------------ | -------------------------------------------------------------------- |
| **CI executions**     | {formatCount(gmtStats.executions)}               | {formatCount(executionRange.min)} – {formatCount(executionRange.max)} |
| **Locales tested**    | {gmtStats.locales}, built into every test        | {localeRange.min} – {localeRange.max} files, tested in isolation from the rest of the API surface |
| **Timezones tested**  | {gmtStats.timezones} × every public function     | {timezoneRange.min} – {timezoneRange.max} files, tested in isolation |
| **Node versions**     | {gmtStats.nodes.join(", ")}                      | {nodeRange.min} – {nodeRange.max} |
| **Public functions**  | {formatCount(gmtStats.functions)}                | {publicApiRange.min} – {publicApiRange.max}<sup><a href="#public-api-counts" aria-label="How public functions are counted">*</a></sup> |
| **Time precision**    | Nanoseconds, exact as `bigint`                   | {competitorTimeResolutionLabel()}                                     |
| **Sentinel contract** | `""` / `null` / `false` / `[]`                   | Throws `RangeError`                                                   |

<p id="public-api-counts" class="gmt-table-note">
  <sup>*</sup> Public functions and methods, counted from each library's published
  TypeScript declarations: every exported function, plus every public method of its
  exported classes and types. Overloads, aliases and inherited methods count once;
  constructors, getters and properties do not.{" "}
  {competitorsByPublicApi()
    .map(
      (l) =>
        `${l.displayName} ${l.stats.publicApi.version}: ${formatCount(publicApiTotal(l))} (${l.stats.publicApi.functions} ${l.stats.publicApi.functions === 1 ? "function" : "functions"}, ${l.stats.publicApi.methods} ${l.stats.publicApi.methods === 1 ? "method" : "methods"})`,
    )
    .join("; ")}. GMT exports functions only.
</p>

The table is the point. GMT does not add a few convenience methods to an
existing `Date` wrapper — it replaces the type system entirely with
[TC39 Temporal](https://tc39.es/proposal-temporal/), then rebuilds the
ergonomic surface on top of that guarantee. Every function takes and returns
[ISO 8601](https://www.iso.org/iso-8601-date-and-time-format.html) strings,
every zoned value carries its
[RFC 9557](https://www.rfc-editor.org/rfc/rfc9557) time-zone annotation, and
the {gmtStats.locales}-locale, {gmtStats.timezones}-timezone matrix runs
against the library's *entire* public API on every PR, not a sample of it.
That is what {formatCount(gmtStats.executions)} CI executions verify.

`@northguild/gmt` is not the latest entry in a crowded field — it is a
fundamentally different bet about what a date/time library should guarantee.

## CI test execution volume

The most direct measure of testing rigor is how many times the library is
actually executed in CI. GMT's suite is {formatCount(gmtStats.tests)} tests, and its {gmtStats.locales}-locale
matrix is built into those tests rather than layered on top. On every PR, CI
then re-runs the whole suite under {gmtStats.timezones} timezones and {gmtStats.nodes.length} Node
versions, so every test runs {runsPerTest} times.

## Timezone coverage

GMT tests against {gmtStats.timezones} timezones chosen not for geographic spread but for offset coverage — from UTC−11 (Pacific/Niue) to UTC+14 (Pacific/Apia). That 25-hour window means that at any given moment, at least one zone is already living in tomorrow while another is still stuck in yesterday. Date-boundary bugs — off-by-one day, wrong month rollover, DST gaps — only surface when the suite runs across this full offset range. A test that passes at UTC can fail at UTC+14 simply because the calendar date is different.

## Locale matrix

GMT does not test every locale — there are hundreds, and most differ only in formatting minutiae. Instead it tests a curated matrix of {gmtStats.locales} locales chosen to stress the dimensions that actually break date libraries: script direction (LTR/RTL Arabic and Hebrew), character sets (CJK, Cyrillic, Latin), pluralization rules, and ICU data variants. The goal is not exhaustive locale coverage — it is representative coverage of every class of bug that locale-aware code can produce.

## What this means

| Dimension             | GMT                                              | Legacy libraries                                                    |
| --------------------- | ------------------------------------------------ | -------------------------------------------------------------------- |
| **CI executions**     | {formatCount(gmtStats.executions)}               | {formatCount(executionRange.min)} – {formatCount(executionRange.max)} |
| **Locales tested**    | {gmtStats.locales}, built into every test        | 0 – 42 files, tested in isolation from the rest of the API surface   |
| **Timezones tested**  | {gmtStats.timezones} × every public function     | 0 – 8 files, tested in isolation (Spacetime disables 4 of its own DST-edge-case files, and 41 of the ones it does run currently fail) |
| **Node versions**     | {gmtStats.nodes.join(", ")}                      | 1 – 2 (only Spacetime matches GMT's matrix; the rest test a single LTS) |
| **Public functions**  | {formatCount(gmtStats.functions)}                | 75 – 223                                                              |
| **Sentinel contract** | `""` / `null` / `false` / `[]`                   | Throws `RangeError`                                                   |

The table is the point. GMT does not add a few convenience methods to an
existing `Date` wrapper — it replaces the type system entirely with Temporal,
then rebuilds the ergonomic surface on top of that guarantee. The gap isn't
that legacy libraries skip locale or timezone testing outright — some, like
Day.js and Spacetime, ship plenty of it — it's that none of them run that
coverage against their *entire* API the way GMT's matrix does, and the
tests that exist aren't always trustworthy: Day.js's own timezone tests
assert against `moment`'s output as the oracle, and Spacetime's own DST
tests are currently failing where they haven't been disabled outright.

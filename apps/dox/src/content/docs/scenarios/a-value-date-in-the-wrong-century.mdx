<Scenario
  title="A Value Date in the Wrong Century"
  description="A ten-year swap leg settles on a value date sent as 350615. The receiving system stores a date."
  naiveCode={`// The naive approach: a cut-off of 30 that someone chose, stated through the pattern parser
import { parseDateWithPattern } from "@northguild/gmt/plain/parse";

parseDateWithPattern("350615", "yyMMdd", undefined, { yearWindow: 1930 });
// "1935-06-15" — a century before the settlement date
parseDateWithPattern("750615", "yyMMdd", undefined, { yearWindow: 1930 });
// "1975-06-15" — accepted, and SWIFT refuses it`}
  explanation={`SWIFT states the century for a value date. A year above 79 is in the 1900s, the rest are in the 2000s, and a year after 2060 is refused with error code T50. So 350615 is 15 June 2035. The cut-off above puts it in 1935, a century before the date the payment settles.

The same cut-off accepts 750615 as 1975. SWIFT refuses that value, because the rule puts it in 2075, past 2060. So the check passes the bad data and the system stores a date nobody sent.

The cut-off is a choice someone made, not a rule SWIFT states. parseSwiftDate applies SWIFT's own rule, so there is no choice left to get wrong.`}
  gmtCode={`import { parseSwiftDate } from "@northguild/gmt/finance/parse";
import { isValidSwiftDate } from "@northguild/gmt/finance/validate";

parseSwiftDate("350615"); // "2035-06-15"
parseSwiftDate("750615"); // ""
isValidSwiftDate("750615"); // false`}
  fixedSpecId="parseSwiftDate"
/>

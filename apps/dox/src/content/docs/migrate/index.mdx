GMT follows the Temporal specification. Moving to it from a date library changes the same few things whichever library you leave, so they are listed once here. Each library page then maps its calls one by one.

## What changes

- **Strings in, strings out.** A GMT value is a string in ISO 8601 form, with the RFC 9557 `[zone]` suffix for a zoned value. There is no object to construct, and a string cannot change after you make it. Check one with a validator such as `isValidDate` or `isValidZonedDateTime`.
- **Bad input gives a typed fallback.** A function that cannot read its input returns `""`, `null`, `false` or `[]` for its return type, and does not throw. A correct empty result, such as two intervals that do not overlap, is `[]` too, so read the function's page for what its fallback means.
- **Months run from 1 to 12.** This matches Temporal. A library that counts from 0 needs each month number moved by one.
- **No token formatter.** GMT formats through `Intl` with a locale and a style, as in `formatDate(value, "de-DE", { dateStyle: "long" })`. It does not read tokens such as `dd/MM/yyyy` when it writes. `parseDateWithPattern` reads them.
- **A day in a zone is a calendar day.** Adding one day to a zoned value gives the same wall-clock time on the next date, as Temporal does. Adding hours adds exact time.

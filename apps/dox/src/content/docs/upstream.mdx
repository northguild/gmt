GMT is built on [Temporal](https://tc39.es/proposal-temporal/), the new JavaScript date and
time standard. Node and some browsers now have Temporal built in, but GMT runs on the community
[`@js-temporal/polyfill`](https://github.com/js-temporal/temporal-polyfill) everywhere, so it gives
the same answer on every runtime. Every week, GMT's whole test suite also runs on the built-in
engines.

**If you use GMT, there is nothing on this page for you to do.** The polyfill has a handful of bugs
in rare corners of the calendar. GMT spots each one and gives you the right answer anyway. The rest
of this page is the detail: which bugs, and what we have done to get them fixed for everyone.

We test GMT against the Temporal standard itself, never against the polyfill, so we can see when the
polyfill is wrong. When it is, we send the fix to the people who maintain the polyfill, and to the
Temporal standard's own reference code where the same bug lives there too.

## How a fix reaches you

The polyfill is being brought back in line with the current version of the standard, one change at a
time. It is a long job, and it decides where each fix has to go:

- **The standard first.** Its maintainers asked us to send fixes to the Temporal standard rather
  than straight to the polyfill, so that the catching-up work stays manageable.
- **The polyfill next.** Fixes arrive there as that work moves forward. This is why several of the
  pull requests below were closed with thanks instead of merged. None was turned down; each was sent
  where it would do more good.
- **A release last.** The maintainers would rather publish one release once the polyfill has caught
  up than a release for each fix.

Until that release, GMT's own code covers every bug in the table above.

## Why this polyfill

There are two Temporal polyfills: [`@js-temporal/polyfill`](https://github.com/js-temporal/temporal-polyfill),
which GMT uses, and [`temporal-polyfill`](https://github.com/fullcalendar/temporal-polyfill) from
FullCalendar, which is smaller and publishes releases more often. We ran GMT's whole test suite on
`temporal-polyfill` to see whether GMT should switch.

Release 1.0.8 fixes most of the bugs in the table above, and the five bugs we reported in
`temporal-polyfill` 1.0.6 and 1.0.7. Its UTC offsets match `Intl.DateTimeFormat` in every time
zone, on every day from 1970 to ten years ahead. On Node, GMT's whole test suite passes on it
with no test failing that passes on `@js-temporal/polyfill`. Release 1.0.7 had two bugs that
1.0.8 fixes:

- **Looking back from far ahead.** Asked for the last clock change before a date more than about
  three years from today, 1.0.7 returned an older one. Asked on 4 November 2026 about June 2030 in
  `America/New_York`, it returned the change in November 2029, not the one in March 2030. Twelve of
  GMT's tests failed on this. We reported it as #125.
- **Before 1847.** 1.0.7 did not find clock changes before 1847, such as `Asia/Manila` on
  31 December 1844. We reported it as #126. GMT works around the same bug in
  `@js-temporal/polyfill`.

One bug is left, and the maintainers closed its report as a known limitation:

- **Zone names that are links.** It treats a link name such as `Asia/Calcutta` as a different
  zone from `Asia/Kolkata`. FullCalendar's report of this, #118 (not ours), was closed as a known
  limitation. GMT's own probe sees it in WebKit as `Etc/UTC` not equal to `UTC`.

So for now GMT stays on `@js-temporal/polyfill`. Every week, GMT runs its whole test suite on the newest
`temporal-polyfill` release in Node and three browsers. It checks every zone's offsets against
`Intl.DateTimeFormat` and every calendar's years against Node's built-in Temporal. A release that
passes all three opens an issue in GMT's repository, and that
issue starts the switch. See the
[weekly runs](https://github.com/northguild/gmt/actions/workflows/temporal-oracle.yml). The full
comparison is in GMT's repository:
[`temporal-polyfill-swap.md`](https://github.com/northguild/gmt/blob/main/context/domination/research/temporal-polyfill-swap.md).

## What this means for you

**You don't need to do anything.** Where the polyfill has one of these bugs, GMT uses its own
correct code instead. It checks once, as it loads, whether the installed polyfill still has each
bug; where the bug is gone, GMT uses the polyfill directly. You get the same correct answer either
way.

So when a polyfill release carries these fixes, GMT's extra code simply stops being used. Your
results don't change, which is the point: there is nothing here for you to keep track of.

These checks run on their own, so nobody has to remember them. Every bug on this page has a test
that runs against the installed polyfill, and GMT's answers are compared with the Temporal built
into Chrome — date by date, across every calendar GMT supports. For GMT {gmtVersion} that comparison
found no differences.

## Native engines

Every week, GMT runs its whole test suite on the Temporal built into Node 26, Chromium,
Firefox and WebKit, and expects the same answers it gets on the polyfill. A failure that no known bug
explains opens an issue in GMT's repository. Each run lists the exact engine versions it used:
see the [weekly runs](https://github.com/northguild/gmt/actions/workflows/temporal-oracle.yml).

The built-in engines have a few bugs of their own. We report each one we find. The list so far:

- [`unicode-org/icu4x#8620`](https://github.com/unicode-org/icu4x/issues/8620): Node and Chromium
  reject a one-letter annotation key, such as `[a=bc]`, which the standard allows.
- [`boa-dev/temporal#529`](https://github.com/boa-dev/temporal/issues/529): Node and Chromium
  accept the calendar `islamic`, which the standard says to reject.
- Node 26 throws when it rounds to the day on a date that starts twice, such as 6 November 2010
  in `America/Goose_Bay`. Chromium 153 already has the fix, so a later Node will have it too.
- [`ICU-20548`](https://unicode-org.atlassian.net/browse/ICU-20548): Node, Chromium and Safari
  shorten a long zone name in a time range, and drop an offset name such as `GMT-5`.
- [Bugzilla 1998020](https://bugzilla.mozilla.org/show_bug.cgi?id=1998020): Firefox accepts a
  zoned date on 19 April −271821, just outside the range the standard allows.
- [Bugzilla 2085525](https://bugzilla.mozilla.org/show_bug.cgi?id=2085525): Firefox prints AM and
  PM in a time range that asks for a day period such as "in the morning", when a zone name is shown.
- WebKit adds a year to the 30th of Dhu al-Hijjah in an Islamic year before the Hijra as 13
  months, so the result lands a month late. The report to WebKit is pending.
- WebKit throws when it adds a year to the last day of Chaitra in a year before about
  4800 BCE. The report to WebKit is pending.

GMT gives the standard's answer in every case.

## What kind of bugs are these?

They're rare edge cases. Most only show up:

- near the very first or very last date Temporal can represent (around the year 275,000);
- in non-Gregorian calendars, such as Hebrew, Persian, Islamic or Japanese;
- in time zone history from before the 1850s; or
- in a time zone whose clocks changed twice within a few weeks, such as `Africa/El_Aaiun` in 1976.

Temporal is a large, carefully designed standard, and the polyfill is a big piece of work.
Finding bugs like these is normal. We found them because GMT tests the unusual corners that
most code never reaches.

We sent them to two places:

- **The polyfill** ([`js-temporal/temporal-polyfill`](https://github.com/js-temporal/temporal-polyfill)),
  the package GMT and many other projects install. Some of its fixes are already written but
  not yet in a published release, so we've asked for a new release. That would also fix two
  bugs other users had already reported.
- **The Temporal proposal** ([`tc39/proposal-temporal`](https://github.com/tc39/proposal-temporal)),
  which has its own reference copy of the same code. Where a bug exists there too, we reported
  it with the same fix, so it's corrected at the source. We also asked one question about the
  standard's own text: it refuses a string that it writes itself, for a few hours at the very
  start of the range.

## How we check each fix

- The correct answer comes from the Temporal standard, its official test suite (test262) and the
  Temporal built into Chrome. We never use the polyfill's own answer as the reference.
- Each fix is tested on a real build of the polyfill, with and without the change, using the
  exact example in the report.
- We also check that the fix doesn't change any answer that was already right.

Every example and fix is written up in full in GMT's repository:
[`js-temporal-polyfill-bugs.md`](https://github.com/northguild/gmt/blob/main/context/domination/js-temporal-polyfill-bugs.md).

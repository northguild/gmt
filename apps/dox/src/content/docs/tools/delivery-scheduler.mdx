Each leg below is a departure, a duration and the zone it lands in. Every
handoff — where one leg's arrival, plus its dwell, becomes the next leg's
departure — is an exact instant, never a wall-clock guess.

The summary card leads with the answer: the ETA, in the last leg's own zone,
with the exact instant kept on a muted line underneath, the door-to-door span,
and small flags for what happened along the way — a DST change, a Date Line
crossing, an offset-table disagreement. A missed connection turns the same
card into a plain failure state naming the leg.

Below it, a toggle switches between two charts of the same journey. **Route**
draws it as a schematic line — one segment per leg, numbered and coloured,
never sized by how long the leg actually took, so an eleven-day sea crossing
and a two-and-a-half-hour rail leg read as the same length. **To scale** draws
the same legs as lanes on a real time axis instead, so the eleven days and the
two and a half hours read as what they are; a handoff shows as a lighter bar
in the gap, and a missed connection as a broken link with a "missed" marker.
Both mark every DST or Date Line crossing along the way. The itinerary
underneath lists the same journey the other way, top to bottom: every
departure, arrival and handoff on a rail in its leg's own colour, grouped by
the local date each one falls on, with DST and Date Line notes as small
annotations beside the line.

Where a fixed offset would misread a handoff, both views flag it — the Los
Angeles arrival 1 h early, in the default journey below — against the offset
table's naive reading. That reading is the only value the widget computes
itself, and it is always labelled as what it is: a naive reading, not the
answer.

The journey list and the outputs below are the real
[`scheduleDelivery`](/reference/transport/calculate/scheduleDelivery/) call
for what is on screen.

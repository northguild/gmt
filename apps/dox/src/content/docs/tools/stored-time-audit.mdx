<Fragment slot="keypoint">

A zoned time you stored last year can mean something else today. When a country changes its rules, a time written with the old offset may no longer match the zone, or may fall in an hour that no longer exists.

</Fragment>

<Fragment slot="intro">

A stored zoned time carries three parts: a local date and time, a UTC offset and a zone name. They agree only while the zone's rules do not change. Governments change them often: Turkey stayed on +03:00 in 2016, Morocco moved to +01:00 in 2018 and Brazil dropped daylight saving time in 2019. A time stored before the change keeps the old offset, and the zone now says something else.

Paste one stored time per line, or pick a preset. The table gives each line a kind and the readings it still has. Choose a line and the strip below draws the rule that matters: a skipped or repeated hour for a clock change that day, or the offset the zone has held since a change for an offset that no longer matches. Under it are the exact calls and the answer as the library returns it.

</Fragment>

<Fragment slot="after">

**The five kinds.** [`classifyStoredZoned`](/reference/zoned/classify/classifyStoredZoned/) reads the three parts against the zone's rules and returns one of five kinds.

- `valid`: the offset is the zone's offset at that time. The string names one instant.
- `validInOverlap`: the time falls in a repeated hour and the stored offset picks one of the two readings.
- `offsetMismatch`: the stored offset is not the zone's offset at that time. The result holds both instants, `atStoredOffset` and `atZoneOffset`.
- `ambiguous`: the time falls in a repeated hour and the offset is neither reading, so there are two possible instants.
- `nonexistent`: the time falls in a skipped hour. The result holds the `earlier` and `later` instants around it, and `atStoredOffset`.

**Choosing a reading.** The function does not decide which instant you meant. It gives you every reading, and the one you take depends on what the stored offset was for.

| Kind | What you have | Take |
| --- | --- | --- |
| `valid` | one instant | the instant |
| `validInOverlap` | one instant, in a repeated hour | the instant |
| `offsetMismatch` | two instants | `atStoredOffset` if the offset was recorded at the event, `atZoneOffset` if the wall time was |
| `ambiguous` | two instants | `earlier` or `later`, by your own rule |
| `nonexistent` | two instants and one at the stored offset | `atStoredOffset` if the offset was recorded, else `earlier` or `later` |

**The answer depends on the host.** The zone's rules come from the time zone database that the runtime carries. A browser does not say which release it has, so the same line can read differently on another device or server. A runtime built before a rule change reads a time by the old rules. If Vancouver's rules change, a time stored there reads by the old ones on a device that has not updated yet. On Node, `process.versions.tz` names the release, so keep it with the data you audit.

```ts
classifyStoredZoned("2016-12-01T09:00:00+02:00[Europe/Istanbul]");
// { kind: "offsetMismatch", storedOffset: "+02:00", zoneOffset: "+03:00",
//   atStoredOffset: "2016-12-01T07:00:00Z", atZoneOffset: "2016-12-01T06:00:00Z" }
classifyStoredZoned("2026-03-08T02:30:00-03:00[America/Los_Angeles]");
// { kind: "nonexistent", earlier: "2026-03-08T09:30:00Z",
//   later: "2026-03-08T10:30:00Z", atStoredOffset: "2026-03-08T05:30:00Z" }
classifyStoredZoned("not a time"); // null
```

A string that is not a stored zoned time, such as a time with no offset or a zone that does not exist, returns `null`, and the tool shows `NO SIGNAL` with the reason. That is different from a line that is `valid`, which is a real answer.
